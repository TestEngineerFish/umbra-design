# Umbra Studio · 17 问题登记规范（GitHub issues）

> **这份文件只管一件事：发现的问题怎么登记成 GitHub issue。** 问题本身的状态在 `12` §九；
> 发现方法在 `04` §二。仓库：`TestEngineerFish/umbra-studio`。
> 口径沿用用户的《Umbra定时测试任务模版》，这里只留和本项目有关的部分。

## 一、什么算一条

- **一条 issue 只说一个问题**，能独立修、独立关。两处症状同一根因 → 一条；同一处两个根因 → 两条。
- 每条要标 **【确证】**（有可复现的读数或代码证据）或 **【判断】**（推断，未复现）。拿不准的不报 —— `04` §二「不许误报」对 issue 同样成立。
- 已经修掉的问题也登记（带 commit），为的是可追溯；登记后立刻关。

## 二、标题与标签

- 标题：`[bug] …` / `[idea] …` / `[chore] …`，一句话说现象，不说原因。
- 标签（都要预先存在）：`type:bug | type:idea | type:chore` · `from:review | from:radar | from:user` · `p0 | p1 | p2` · 需要用户定的加 `待拍板`。
  - `p0` 主流程走不通（打不开项目、落盘失败）· `p1` 一个功能不可用或明显误导 · `p2` 体验 / 打磨。
  - `from:user` 是用户报的；`from:review` 是看代码看出来的；`from:radar` 是扫测（Playwright / 壳内自测）抓的。

## 三、正文格式

```
<!-- fp: review/umbra-studio/<文件路径>#<英文短标识> -->
来源：<谁发现的> ｜ 证据：<文件>:<行> 或 <脚本 / 读数>
发现方式：<一句话>

### 位置
### 为什么是问题
### 影响面
### 怎么修
```

首行 `fp` 是**指纹**，用来查重：提交前先查
`search/issues?q=repo:TestEngineerFish/umbra-studio+is:issue+"fp: <指纹>"+in:body`，有就不再建。
「怎么修」写到能动手的程度；已修的写 commit 短 sha 与实测读数。

## 四、提交方式

- 草稿放 `issues/<日期>/NN-<slug>.md`（frontmatter：`title`、`labels`），脚本 `issues/post.sh` 批量提交（查重、建缺的标签、已修的顺手关）。
- token 读 `~/Documents/SourceTree/Geek/.secrets/gh-token`，**不打印、不进 issue 正文**；任何密钥都不进 issue。
- git 命令带 `GIT_OPTIONAL_LOCKS=0`。
- 提交成功后把 issue 号回填到 `12` §九 那张表。
