# UmbraDesign · 09 三层修改路径

> 这一份是**架构分析与决策文档**，不是实现记录。
> 起因：这个工具最终要支持三层修改，而现在只建好了第三层。
> 前两层不是「以后再加的功能」—— 它们要求的东西**现在不埋就得返工**，
> 因为它们改的是每个工具返回的数据形状。
>
> 需要拍板的都集中在 §四，正文只讲依据。

---

## 一、三层是什么，各自要什么

| 层 | 谁在改 | 一次交互的形状 |
| --- | --- | --- |
| **L1 手动调属性** | 人，直接改 | 选中一个节点 → 拖滑块 / 选颜色 → 稿变了 |
| **L2 选中后告诉模型** | 人指位置，模型改内容 | 选中一个节点 → 说「这里改成 X」→ 模型改 → 人看结果 |
| **L3 Agent 直接沟通** | 别的大模型，全程无人 | 提需求 → 读规则与取值 → 写稿 → 校验 → 体检 → 回报变更 |

L3 是已经建好的那一层（24 个工具，`00` §十～§十六）。

**L1 和 L2 共同要求两件现在没有的东西**，而且两件都是**数据形状**问题
—— 不是加个工具就完事，是每个返回都要带上：

1. **节点地址** —— 人在预览里点的那个东西，怎么对应到源码里的那一处
2. **每个洞的来源** —— 这个值是模板里的字面量（人能直接改），
   还是 `renderVals` 给的（要改逻辑类），还是算出来的（人改不了，只能让模型改）

第 2 件的机器已经有了 —— 就是洞审计（`00` §十六）。
但它现在只输出「这份稿审了/没审」加一个键名并集。L1 要的是**逐洞**的答案。

---

## 二、L2 的缺口：节点地址

### 2.1 链条断在第一环

L2 要走通的链条是：

```
预览 iframe 里的 DOM 节点 → 源码里的位置 → 模型能照着改的描述 → 落得下去的编辑
```

现在：iframe 预览有（S2、静态服务）、模型能改（`patch_draft`）、
落盘有唯一入口。**断的是第一环** —— 点中一个 div，没有任何东西能说出
它是源码第几行那个元素。

而且这不是「加个 map」就行：`sc-for` 让它天然是**一对多**
（一处源码 → N 个 DOM 节点），`dc-import` 让它**跨文件**。

### 2.2 三种地址方案，前两种不能用

| 方案 | 问题 |
| --- | --- |
| 源码偏移 / 行号 | 上面插一行，下面全错。人改一次就失效 |
| 结构路径 `/x-dc/div[0]/div[2]` | 插一个兄弟节点，后面全错。**而且 `07` §2.4 已经因为同样的理由否掉了按路径配对** |
| **节点指纹**（短哈希） | 只在节点**自己**变的时候变；别处怎么改都不影响 |

指纹这套机器 `snapshot.ts` 已经有了 —— 语义 diff 的 LCS 配对就是靠它，
而且在 6,323 节点的真稿上验过。**结论（有依据）：用指纹，不用路径。**

已知限制，说清楚：**一个节点被改之后它的 id 会变。** 对「选中」没影响
（人重新选一次），对 L1 的写入有影响 —— 所以写入的返回里必须带**新 id**，
让界面接着往下调。这一条不绕过，写进契约。

### 2.3 DOM 里怎么拿到这个 id —— 已实测

想让预览里的 DOM 认得自己，直觉方案是改 `support.js`，让它在建节点时打标。
**这条路走不通：`support.js` 我们只有编译产物，没有源码**（`05` §一）。

可行的那条路是：**落盘时把 id 写成普通 `data-` 属性**。
和 `__resources` 注入同一套做法（`00` §14.7）—— 源稿保持抽象，落盘副本带上它。
普通属性 `support.js` 会原样搬进 DOM，不需要它配合。

**实测（容器里真渲染，不是推理）：**

源稿三种位置各放一个 `data-ud-id`：静态节点、`sc-if` 里的节点、`sc-for` 里的节点。

| 源码位置 | DOM 里的 id | 节点数 |
| --- | --- | --- |
| 静态 `<div data-ud-id="n1">` | `n1` | 1 |
| `sc-if` 里的 `data-ud-id="n2"` | `n2` | 1 |
| `sc-for` 里的 `data-ud-id="n3"` | `n3` | **3（三个克隆都带）** |

同一处源码的三个克隆**带同一个 id** —— 这正是「选中源码里的这个元素」
该有的语义，不用额外处理。同一行上的 `style="padding:{{ pad }}px"`
照常解析成 12px，属性和洞互不干扰。

**结论（有依据）：节点地址可行，且不需要动 `support.js`。**

### 2.4 跨文件：id 要带文件名

`dc-import` 进来的子组件，它内部节点带的是**子文件**的 id。
所以 DOM 上光有 `data-ud-id` 说不清是哪份稿的节点。
地址形态定为 **`<稿相对路径>#<短哈希>`**，落盘时写两个属性
（`data-ud-file` + `data-ud-id`），或写一个合起来的。§四 决策 2。

## 三、L1 的缺口：改得动什么，和怎么只改一处

### 3.1 「这个属性能不能改」是洞审计的问题

人选中一个节点，界面要决定给他什么控件。三种情况，处理完全不同：

```html
<div style="padding:8px">                     ← 字面量，滑块直接改
<div style="padding:{{ pad }}px">             ← 洞。改哪里取决于 pad 是什么
```

`pad` 的三种可能：

| `renderVals` 里 | 人能不能直接改 | 界面该给什么 |
| --- | --- | --- |
| `pad: 8` （字面量） | 能 | 滑块，改逻辑类里那个字面量 |
| `pad: P.pad ?? 8` （来自 props） | 不能直接改 | 告诉他「这个值由调用方传入」 |
| `pad: dense ? 4 : 8` （算出来的） | 改不了 | 转 L2：让模型改 |

**没有这个分类，L1 的界面只能瞎给控件** —— 给了一个改不动的滑块，
拖完没反应，比不给更糟。

这正是洞审计能算的东西，而且它已经在走 `renderVals` 的 return 对象了
（`draft.ts auditRenderVals`）。差的是：现在只收键**名**，要改成连键的
**值形态**一起收。工作量不大（§四 决策 3）。

> `00` §十六 把放弃审计的稿从 25 份压到 3 份 —— 那一改当时看是「减少漏报」，
> 放到 L1 的视角就是**可编辑性地图的覆盖率从 56% 提到 95%**。
> 剩下 3 份里 2 份没有 `renderVals()`（本来就没有洞要审），
> 真正审不了的只有 1 份。

### 3.2 属性级写入：现有两个入口都不够

| 现有 | 为什么不够 |
| --- | --- |
| `write_draft`（整文件） | 拖一次滑块重写整份 6,000 元素的稿，还要模型把全文再吐一遍 |
| `patch_draft`（锚点文本） | 锚点是文本匹配。`padding:8px` 在一份稿里出现 40 次，命中多次就报 `E_PATCH_ANCHOR` |

L1 需要的是 **`set_prop(project, path, node, kind, name, value)`**，
`kind ∈ style | attr | text`。三条硬要求：

1. **只动目标那一处**，其余字节不变（滑块会连续调用几十次，不能每次重排文件）
2. **目标是洞就拒绝**，并回报「改 `renderVals` 里的 `pad`」——
   而不是默默把洞覆盖成字面量（那会把一个联动的值改成死值，是静默破坏）
3. **走同一条落盘路** —— 校验 / 归一化 / 快照 / changelog 一样不少

### 3.3 撤销

人拖滑块必然要撤销。快照序列已经在了（`.umbradesign/snapshots/v<N>.json`），
但**没有 `revert_to(v)`**。L1 上线前必须有。§四 决策 4。

## 四、要你拍板的（集中在这里）

| # | 决策 | 我的建议 | 依据 / 可行性 |
| --- | --- | --- | --- |
| 1 | 节点地址用指纹还是路径 | **指纹** | 有依据：`07` §2.4 已因同样理由否掉路径；指纹机器在 6,323 节点真稿上验过。可行性 ✅ |
| 2 | id 怎么进 DOM：改 `support.js` / 落盘注入 `data-` 属性 | **落盘注入** | 有依据：已实测三种位置全通过，`sc-for` 克隆带同一 id。改 `support.js` **不可行**（只有编译产物，没源码）。可行性 ✅ / ❌ |
| 3 | 洞审计是否扩成「逐洞来源分类」 | **扩** | 判断：L1 的界面没有它只能瞎给控件。工作量小（机器已在走 return 对象）。可行性 ✅ |
| 4 | L1 上线前是否必须有 `revert_to(v)` | **必须** | 判断：拖滑块没有撤销不能给人用。快照序列已在，只差一个工具。可行性 ✅ |
| 5 | `任务.dc.html` 的 `decideMeta` / `decideActions` 该填什么 | **要你或 ClaudeDesign 定** | `00` §16.3 抓出的真缺陷。那张错误卡该显示哪几行信息、几颗按钮，是设计决定，我不替你定 |
| 6 | L1 的改动是否进 `CHANGELOG-设计侧.md` | **进** | 判断：不进就是 `07` 的变更交付有个洞 —— 人手动改的 padding，实现侧永远不知道。代价是清单变吵，可以按级别过滤（L2 取值级） |
| 7 | 这些什么时候做 | **第二批开头，`bundle_draft` 之前** | 判断：地址与来源分类改的是**每个工具的返回形状**，越晚埋返工面越大。`bundle_draft`（形态 B）反而可以再等 |

### 4.1 如果决策 1–4 都按建议走，第二批的形状

1. `snapshot.ts` 的指纹提取成节点地址；`prepareForDisk` 落盘时注入 `data-ud-*`
2. `auditRenderVals` 输出逐洞来源（`literal` / `props` / `computed` / `unknown`）
3. 新工具：`locate_node`（DOM id → 源码位置 + 可编辑性）、`set_prop`、`revert_to`
4. `get_index_data` / `validate_draft` / `diff_drafts` 的 `locator` 统一带节点地址
5. S2 预览壳接上点选（iframe 里 `postMessage` 回外层）

**没承诺的**：`bundle_draft`（形态 B）两点仍未验证（`00` §九），继续不承诺。
