# Umbra Studio · 07 变更交付

> 设计侧改了稿，实现侧怎么用最小成本知道**改了什么、要不要动代码**。
> 工具签名见 `00` §5.4。

---

## 一、为什么不能用文本 diff

对 `.dc.html` 做文本 diff 是没用的，三条原因：

1. **样式全写在 `style` 属性上**（`01` §3.3）。挪一个 flex 容器能改四十行，
   而这四十行里真正的设计变更可能只有一个 `padding`。
2. **一份稿一两千个标签**。新增一个 `sc-if` 分支会让整段缩进全变，diff 里全是假变更。
3. **实现侧要的不是"两个版本的文件"，是"我要改什么"。** 文本 diff 回答不了
   「这次要不要动代码」——而这是实现侧唯一真正想知道的事。

现有做法（设计侧自己读一遍再手写一份说明）把这件事变成了每一轮的固定开销。

> **方案：不 diff 文件，diff 语义。**
> 把 `.dc.html` 编译成一份归一化的语义快照，对两份快照做结构化对比，
> 输出按「要不要动代码」分级的变更清单。

## 二、语义快照

### 2.1 抽什么

`.dc.html` 里的**设计事实**是可结构化抽取的：

| 抽出来的 | 来源 |
| --- | --- |
| props 契约 | `data-props` 的 JSON |
| 初始 state | 逻辑类的 `state = {…}` |
| 模板输入键 | `renderVals()` 的顶层键（**每一条返回路径的并集**） |
| 状态分支 | 所有 `<sc-if>` 的 `value` 洞名 |
| 列表 | 所有 `<sc-for>` 的 `list` 洞名与 `as` 别名 |
| 子组件引用 | 所有 `<dc-import>` 的 `name` 与传入的 props |
| 用到的 token | 所有 `var(--x)` |
| 文案 | 文本节点 + 字面量属性（`title` / `placeholder` / `aria-label` …） |
| 节点与取值 | 元素树 + 每个元素归一化后的 `style` map 与属性 map |

### 2.2 快照格式

落在 `.umbrastudio/snapshots/<稿名>/v<N>.json`：

```json
{
  "schema": 1,
  "file": "日志.dc.html",
  "version": "v217",
  "capturedAt": "2026-09-17T08:40:12+08:00",
  "sourceSha256": "…",
  "gitCommit": "a1b2c3d",
  "stats": { "elements": 812, "holes": 143, "imports": 4 },

  "props": { "kind": {"editor":"enum","options":["empty","error"],"tsType":"'empty'|'error'"} },
  "state": { "filter": "all" },
  "valKeys": ["rows", "setAll", "chipStyle", "onRetry"],
  "branches": [ { "id": "b3", "cond": "hasFailed", "at": "L128" } ],
  "lists":    [ { "id": "l1", "list": "rows", "as": "r", "at": "L140" } ],
  "imports":  [ { "name": "../Components/窗口骨架", "props": {"active":"日志"}, "at": "L12" } ],
  "tokensUsed": ["--danger-soft", "--ink-mute", "--text"],
  "texts":    [ { "id": "t7", "at": "L96", "text": "这个月还没有记账" } ],
  "nodes": [
    {
      "id": "n41", "at": "L128", "tag": "div",
      "fp": "div|border-radius,color,padding|…",
      "style": { "color": "var(--ink-mute)", "font-size": "12px", "padding": "6px 10px" },
      "attrs": { "role": "listitem" },
      "holes": ["r.name"]
    }
  ]
}
```

`at` 是**给人定位用的行号**，不是节点身份。节点身份见 §2.4。

### 2.3 归一化规则（做不对，噪声就吃掉信号）

这一步是整个方案的成败点。逐条：

| 项 | 规则 |
| --- | --- |
| `style` | 解析成 map，键按字母序；值内空白折叠 |
| 数值 | `0px` → `0`；`10.0px` → `10px`；`.5` → `0.5`；单位保留 |
| 颜色 | hex 统一小写并展开三位简写（`#FFF` → `#ffffff`）；`var()` 原样保留 |
| 属性 | 存 map，**顺序无关**；值内换行折叠 |
| `class` | 类名拆开排序（虽然 `01` §3.3 不建议用类，运行时确实注入了一组原子类） |
| 文本 | `trim`，内部连续空白折成一个空格；纯空白文本节点丢弃 |
| 注释 | 全部剔除 |
| 标签 | 自闭合与显式闭合视为等价 |
| 大小写 | 标签名与属性名小写；属性值保持原样 |

### 2.4 ⚠️ 节点配对不能靠路径

结构路径（`section/div[0]/span[1]`）在插入一个元素之后会让后面全部偏移，
**靠路径相等来配对会把一次插入报成几十处变更**。

做法：给每个节点算一个**内容指纹** `fp`（标签名 + 归一化 style 的键集 + 文本/洞的摘要），
diff 时按「同层最长公共子序列 + 指纹相似度」配对，配不上的才算新增或删除。

> 这是唯一一处算法上有真实难度的地方。**先按同层 LCS 实现**，
> 跨层移动（把一个 div 从 A 挪到 B）第一版允许报成「删除 + 新增」，
> 在 `L4 等价` 级里注明「疑似移动」。不要为了完美的树 diff 卡住第一批。

## 三、四级分类

**分级的目的只有一个：让实现侧知道要不要动代码。**

| 级 | 名字 | 含义 | 实现侧动作 |
| --- | --- | --- | --- |
| **L1** | 契约 | 接口变了 | **必须改代码** |
| **L2** | 取值 | 数值 / 颜色 / 间距变了 | 照抄新值 |
| **L3** | 文案 | 字符串变了 | 改字符串 |
| **L4** | 等价 | 渲染无净变化 | 无需处理，**默认折叠** |

### 3.1 各级的判定

**L1 契约** —— 命中任一条：

- `props` 新增 / 删除 / `tsType` 变化 / `editor` 从 `null` 变成非 `null`（反之亦然）
- `branches` 新增 / 删除 / `cond` 改名 —— 状态清单变了
- `valKeys` 里的**事件或 ref 键**（`on*` / `*Ref`）新增 / 删除 / 改名
- `lists` 的 `list` 洞改名，或 `as` 别名变化
- `imports` 新增 / 删除，或传给子组件的 props 键变化
- `state` 新增 / 删除键

**L2 取值** —— `nodes[].style` 的键值变化、`tokensUsed` 的增删、
节点上 `var(--a)` → `var(--b)` 的替换。

**L3 文案** —— `texts` 变化，以及 `title` / `placeholder` / `aria-label` 等
字面量属性的值变化。

**L4 等价** —— 配对成功但两边归一化后完全相同的节点重排；
包裹层增删且样式无净变化；疑似跨层移动。

### 3.2 一条判定纪律

**分级只看快照差异，不猜意图。** 拿不准的往高一级报——
把一次取值变更误报成契约级，实现侧多看一眼；
把契约变更漏报成取值级，实现侧的代码就是错的。

## 四、输出

`diff_drafts` 同时出两种，同一份数据两个投影：

### 4.1 JSON（给工具与模型）

```json
{
  "file": "日志.dc.html", "from": "v216", "to": "v217",
  "changes": [
    { "level": "L1", "kind": "prop_added",
      "target": "onRetry", "to": "() => void", "at": "L45",
      "message": "新增 props onRetry: () => void",
      "impact": "实现侧需要接这个回调" },
    { "level": "L2", "kind": "style_changed",
      "target": "日志行", "prop": "line-height",
      "from": "20px", "to": "22px", "at": "L131" }
  ],
  "counts": { "L1": 2, "L2": 5, "L3": 3, "L4": 2 }
}
```

### 4.2 Markdown（给人）

```
《日志.dc.html》  v216 → v217

[契约 · 必须改代码]
```

## 五、`CHANGELOG-设计侧.md`

**实现侧只读这一份。** 它是纯文本、可 grep、跟稿一起走，
即使对方没装 MCP 也能用——这是降级路径。

`write_draft` 每次落盘自动在文件顶部插入一节（**倒序，最新在上**）：

```markdown
# 设计侧变更 · Umbra_design_next

> 实现侧只读这一份。级别含义：
> [契约] 要改代码 · [取值] 照抄新值 · [文案] 改字符串 · [等价] 无需处理

## v217 · 2026-09-17 08:40 · 日志.dc.html
...（§4.2 的正文）

## v216 · 2026-09-16 19:02 · 能力.dc.html
...
```

写入纪律：

- **只有 L1 / L2 / L3 里至少一条非空才写入。** 纯 L4 的落盘不写 changelog，
  否则清单很快就没人看了。
- 版本号 `v<N>`：`N` 取 `.umbrastudio/snapshots/<稿名>/` 下已有的最大值 + 1，**按稿独立计数**。
- 同一份稿在**同一分钟内**的多次落盘合并成一节（模型常常连着改几刀）。

## 六、跨版本净变更

`get_changes_since(project, since, paths?)` 回答的是
「我实现的是 v217，现在最新 v221，我要改什么」——**不是把四份 diff 拼起来**。

合并规则：

| 情况 | 净结果 |
| --- | --- |
| 同一属性多次变化 | 只报最终值（`20px → 22px → 24px` 报成 `20px → 24px`） |
| 新增后又删除 | **不报** |
| 删除后又新增（值不同） | 报成"改" |
| 删除后又新增（值相同） | **不报** |
| 级别不同的多条命中同一目标 | 取最高级别 |

出参与 `diff_drafts` 同形，多一个 `spans: ["v218","v219","v220","v221"]` 说明合并了哪几版。

## 七、版本从哪来

**主路径是快照序列，git 是兜底。** 两者的地位不对等，别搞反：

| `from` / `to` 的形态 | 取法 | 需要 git |
| --- | --- | --- |
| `v<N>` | 读 `.umbrastudio/snapshots/<稿名>/v<N>.json` | ❌ |
| 省略 `to` | 用工作区当前内容现算 | ❌ |
| git ref（`HEAD~3`、tag、sha） | `git show <ref>:<path>`，现算快照（不落盘） | ✅ |

前提：**每个设计项目各自一个 git 仓库**，仓库根就是租户目录（`00` §3.3）。
Umbra Studio 自身的仓库不追踪租户——工具不该追踪用户的项目。

`git.enabled` 不用手填，自动探测租户目录下有没有 `.git`。没有 git 时
`v<N>` 那两行照常工作，按 ref 取直接返回 `E_GIT_DISABLED`。

### 7.1 快照进不进租户的仓库

两种都行，租户自己选，差别只有一条：

- **不进**（`.gitignore` 里 `.umbrastudio/`，默认）：仓库干净，
  语义 diff 的历史靠快照文件在本地留存；重装或换机后旧版本只能靠 git 现算。
- **进**：`.gitignore` 里只忽略 `.umbrastudio/shots/` 与 `.umbrastudio/cache/`，
  保留 `snapshots/`。这样变更历史跟着仓库走，代价是每次落盘多一个小 JSON 的提交噪声。

`doc/_模板-租户 .gitignore` 里默认是"不进"，并在注释里写了怎么改成"进"。

## 八、第二批：版本对账

给每份稿在 helmet 里写一行：

```html
<meta name="dc-design-version" content="日志@v217">
```

实现侧在自己代码里记下"我实现的是 `日志@v217`"。
那么「我落后几版、差什么」就能自动回答，不必人去记。

**第一批不做**，因为它要求实现侧那边也配合改流程；先把 changelog 跑顺。

## 九、这一份的验收

- [ ] 同一份稿不改一个字，连续两次 `snapshot_draft` → 快照逐字节相同
- [ ] 只重排一个容器（渲染等价）→ 变更清单里只有 L4，L1/L2/L3 全空
- [ ] 只改一个 `padding` → 只有一条 L2，且行号指对
- [ ] 在模板中间插入一个 `<div>` → **不许**把后面的节点全报成变更（§2.4 的 LCS 生效）
- [ ] 给 props 加一个 `onRetry` → 报 L1，`impact` 写明实现侧要接回调
- [ ] 连改四版同一个 `padding` → `get_changes_since` 只报首末值
- [ ] 纯 L4 的落盘 → `CHANGELOG-设计侧.md` 不新增小节
