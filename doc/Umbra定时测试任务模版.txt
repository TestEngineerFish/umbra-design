## 每次做两件：增量 + 轮扫一片

**增量是主线，轮扫是保证覆盖面不冻结在第一遍。**

> 第一遍审查的覆盖面，是由**那天我知道多少种问题**决定的，不是由代码里有多少问题决定的。
> 只做增量的话，那一天的盲区会**永久保留** —— 而且每次都会报「无新发现」，
> 读起来和「这个仓是干净的」一模一样。
> **每发现一类新问题，整个仓在这一类上都是从没被扫过的。**

**A. 增量（每仓）**
1. 读基线拿 sha。`none` 或没有这条 issue → 这个仓这次走**全量**。
2. `GIT_OPTIONAL_LOCKS=0 git -C <仓> log --oneline <sha>..HEAD` 与
   `GIT_OPTIONAL_LOCKS=0 git -C <仓> diff --stat <sha>..HEAD`。
   **只读，绝不 add/commit/push/checkout。**
3. 审完把 `last-reviewed` 改成当前 HEAD 的 sha。
没有改动的仓增量这一半跳过，小结里说一句「X 仓本次无改动」——
**但轮扫那一半照做**（B 不看 diff）。跑成每天之后，多数天多数仓都会是「无改动」，
**那是正常的，不要因此觉得这一趟白跑** —— 轮扫才是每天真正在推进的那一半。

**B. 轮扫一片（每次一片，三个仓合起来轮，不是一仓一片）**
挑**日期最老的一片**（`none` 优先），**不看 diff，把那一片当第一次审那样通读**，
扫完把日期改成今天。

**一片扫完可能提不出任何东西，那是正常结果** —— 把日期改成今天就行；
它的价值是「这一片在今天这套标准下被看过了」，不是「它产出了几条」。

⚠️ **前一段时间优先扫 umbra-pc 与 umbra-ios 的片** —— 那两个仓一次都没审过
（上次审查范围只有 umbra 仓；`umbra-client/` 虽是端侧代码但住在 umbra 仓里）。
**它们今天的「0 条问题」不是干净，是没查过。**

**C. 新镜头回扫**
如果这次（或实现侧）发现了一类**以前从没查过的问题**，在 full-sweep 表末尾
加一行 `⟳ <这一类的名字> | * | none`，当成一片排进轮扫。
> **一条新的判据，不会自动作用于它诞生之前写的代码。**

**PATCH 基线 issue 之前先 GET 一次拿最新正文**，在那份上改。

## 审什么（先重后轻）
① 安全边界：鉴权、路径拼接、外部输入进 glob/SQL/shell、凭证与密钥、日志里的用户内容
② 数据丢失：删除无回收站、并发覆盖、乐观锁读改写跨连接、缓存过期不了
③ 崩溃与阻塞：同步 IO 进事件循环、无上限的读取/递归、没 await 的清理
④ 正确性：注释与实现不符、类型注解与实现不符、死代码、测试盲区
⑤ 跨仓一致性：一个仓里关于另一个仓的断言（"端上有护栏"这类）**必须去那个仓核**

每条标 **【确证】**（有代码或运行证据）或 **【判断】**（推理，需实测确认）。
拿不准宁可标【判断】—— **一条标错的【确证】比一条没提的问题更贵。**

## 登记
1. 指纹 = `review/<仓>/<文件路径>#<英文短标识>`，**跟着问题走不跟着行号走**。
2. 搜同仓：`GET /search/issues?q=repo:TestEngineerFish/<仓>+is:issue+"fp: <指纹>"+in:body`
   ⚠️ **`is:issue` 不能省** —— 少了它 GitHub 回 **HTTP 422**
   （`Query must include 'is:issue' or 'is:pull-request'`），
   而一次失败的查重**看起来就像「没有命中」** → 直接建出重复条目。
   命中且 open → 只追加一条 comment 说这次的新证据，不新建。
   命中且 closed → **不要重开**，除非这次的改动让它复发了（那时新建一条并链到旧的）。
3. 没命中才 `POST /repos/TestEngineerFish/<仓>/issues`
   - title：`[bug] <一句话说清失败场景>` 或 `[chore] <一句话>`
   - labels：`["type:bug"/"type:chore", "from:review", "p0"/"p1"/"p2"]`，
     需要 sam 拍板的额外加 `"待拍板"`
     p0 = 今天线上就成立、可导致数据泄露/篡改/丢失；p1 = 真实缺陷，本月要处理；
     p2 = 正确性/资源/一致性
   - body 首行 `<!-- fp: ... -->`
     次行 `来源：code-review <日期> ｜ 证据：<文件>:<行>`
     再一行 `发现方式：增量 <sha>..<sha>` 或 `发现方式：轮扫 <片名>`
     然后四段：**位置 / 为什么是问题（含复现或代码片段）/ 影响面 / 怎么修**
     「怎么修」要具体到能直接动手，不要写"建议加强校验"这种
   - 标签**已经建好，别再新建**：type:bug / type:idea / type:chore ｜ from:radar / from:review
     ｜ p0 / p1 / p2 ｜ 待拍板 / wontfix

## 节制
**每次最多 3 条新建**（增量 + 轮扫合起来算）。超了只提最重的 3 条，
其余在小结里列标题、下次再提。

> 这个数是按**每天跑**定的。原稿写的是「每周最多 8 条」，
> 而它给的理由是「一次倒进几十条，队列当天就没人看了」——
> 那条理由约束的是**每周进入队列的总量**，不是每次运行的次数。
> 改成每天之后照搬 8 会变成一周 56 条，正好把它要防的事做成了。
> 3 × 7 = 21，比原来的 8 大约两倍半 —— 头一两个月在补扫从没审过的仓，
> 多提一些是合理的；**等 full-sweep 表里 `none` 少于 1/3 了，把这个数降到 1～2。**

**一条都不提是允许的结果**，不要为了有产出而降低标准。
⚠️ 但**轮扫那一片的日期照样要更新** —— 「扫过了、没发现」和「没扫」必须分得开。
