# 20 · 插件与插件市场需求

> **这份管什么**：插件是什么、能做什么、关在哪、怎么买、怎么装、怎么更新。
> **不管什么**：具体接口签名（等 M11-4 落地后进 `00`）、界面形制（走设计侧 `14`）、
> 条目与进度（在 `12`）、决策来由（在 `11` Q36–Q38）。
>
> 依据：用户 2026-09-26 的规划 + 当天的实测调研（§三的读数都是真跑出来的）。
> 状态：**需求稿**。§九列的待拍板项没定之前，不要按这份改代码。

## 〇、判据

**一句话**：把「某种文件怎么编辑」从主程序里拆出去，做成能单独买、单独装、单独更新的东西；
主程序只保证三件事 —— 装得上、关得住、坏了能卸。

验收这份需求，看四条：

1. 没装插件的用户，程序里**不存在**那部分代码（不是灰掉，是没有）
2. 插件做的任何修改，都能在变更清单里看到、能一键回退
3. 插件**拿不到**我们没给它的东西 —— 这一条要能实测，不是靠信任
4. 断网能用已买的插件；联网只在买、下、更新时需要

## 一、为什么要做

用户给的三个理由，加我补的一条：

| # | 理由 | 对设计的约束 |
| --- | --- | --- |
| 1 | 有的编辑插件体积大 | 按需下载，不进主安装包 |
| 2 | 格式会逐步加，不想为此更新主程序 | 插件与主程序**分别发版**；宿主 API 要带版本号并向后兼容 |
| 3 | 希望能赚钱 | 要有授权，且**离线可用**（用户明确要求） |
| 4 | 〔我补的〕把接口逼完整 | 第一期只有我们自己上架（§七），但**照样关进沙箱** —— 见下 |

**第 4 条值得单独说。** 只有自己上架时，沙箱看起来是给自己找麻烦。
但反过来看：如果第一期我们用「想读哪个文件读哪个文件」的方式写插件，
接口上会留下一堆自己都没意识到的洞；等要开放三方时，那不是加一道墙，是重写。
**墙要在里面只有自己人的时候砌。**

## 二、插件是什么：两个能力面

用户原话：「插件有两个能力，一个是本身赋予预览页面的编辑能力，还有一个就是给大模型调用的编辑能力，
但是这块还没想完整」。下面 §2.2 是补完的部分。

### 2.1 A 面：预览页的编辑能力（人用手改）

在详情区给这种格式一套看与改的界面 —— 对应现在 `app/src/kinds/` 里一个模块声明的
`View` / `Toolbar` / `Corner` / `Panels` / `menu`。

**和现在内置格式的区别在于「画在哪」**：内置格式是我们 React 树里的组件；
插件的 A 面是**它自己的一张网页**，住在自己的 iframe 里（§三解释为什么必须这样）。

我们给它：
- 一块矩形（详情区的正文部分）
- 一份设计 token 的 CSS（跟着主题走，插件不用自己配色）
- 一条 `postMessage` 通道，包装成 `umbra.*` 的 promise 接口

它给我们：一个 `manifest.json` + 一张入口 HTML。

⚠️ **代价要说清楚**：插件画不到自己矩形之外。下拉菜单、浮层、toast 如果由插件自己画，
会被矩形裁掉，而且和主程序的浮层形制对不上。
所以这些**由宿主代画** —— 插件调 `umbra.menu(items)`，菜单出现在我们的浮层层里，
形制和别处一致（`00` §八十二 那套）。

### 2.2 B 面：给大模型调用的编辑能力（AI 改）

**为什么必须有这一面。** 本产品的判据是三种编辑方式在同一个窗口里
（手动改 · 选中后让 AI 改 · 直接说）。如果插件只给 A 面，那么对这种格式来说
**AI 是瞎的** —— 它只剩 `read_file` / `write_file` 读写原始字节：

| 格式 | 只有字节读写时，AI 能干什么 |
| --- | --- |
| 视频 | **什么都干不了**。二进制，而且几百 MB 塞不进上下文 |
| HTML | 能读，但只能做文本外科手术，看不懂结构 |
| 表格 | 能读 CSV，读不了 xlsx |

**所以 B 面才是让一种格式变成「一等公民」的东西**，A 面只是让它能看。

**形状**：和 M11-1 刚做的能力注册表是**同一个契约**（`00` §八十三）。
插件在 `register(host)` 里调 `host.defineCap({ name, summary, input, run })`，
声明一次自动出现在三个门面：

```
插件声明一件能力
      ↓            ↓                    ↓
  MCP 面        本地 HTTP 面       应用内 agent 循环的工具表
（外部模型客户端）  （我们的前端）        （用户在会话里说话时）
```

四条要求：

**① 按需上工具表 —— 这条关乎钱。**
agent 循环每一步都要重发「工具表 + 系统提示 + 全部历史」（`CLAUDE.md` 记着一天烧掉 10 元的教训）。
装了五个插件，如果它们的工具一直在表里，**每一步都多发五套工具描述**。
所以插件工具**只在当前上下文里有那种文件时**才进工具表。

**② 插件的 `run()` 没有任何环境权限。**
它在沙箱里跑，碰不到文件系统。要读写就回调 `host.call("read_file", …)` ——
正好是 M11-1 搬过去的那九件。**权限由 manifest 声明，由我们在宿主进程里核，不在沙箱里核**
（在沙箱里核等于让嫌疑人自己签字）。

**③ 写盘必须走两条写入口。**
纪律① 唯一写入口。插件不能直接写字节，否则快照 / 变更清单 / 一键回退全部失效 ——
而「改错了能退回来」正是用户敢让 AI 动自己文件的前提。

**④ 能力名带命名空间。** `video.trim` 而不是 `trim`，否则两个插件撞名。
宿主在注册时强制前缀 = 插件 id。

**一条我建议现在就定**：B 面**不按调用次数计费**。
按次算必然要联网校验，和「离线可用」直接冲突。买了插件 = 它的能力随便用。

### 2.3 两面的关系

一个插件可以只有 A 面（比如一个更好看的图片查看器）、只有 B 面（比如给 AI 一套 HTML 结构化改写工具），
或者两面都有（视频编辑：人拖时间轴 + AI 能"把前 3 秒切掉"）。
**manifest 里分开声明**，没声明的那一面就不加载 —— 只有 B 面的插件根本不起 iframe。

## 三、沙箱：关在哪（本节读数为 2026-09-26 实测）

用户定的是「插件只能跑在沙盒里，防止后期不可控」。这一条定得对，且它决定了接口长什么样。

### 3.1 先说什么**不是**沙箱

Figma 踩过这个坑：他们最初用 **Realms shim**（在同一个 JS VM 里造隔离），
被反复逃逸 —— 因为沙箱内外**用的是同一个引擎**，攻击者只要让它把外面的对象和里面的对象搞混。
现在换成 **QuickJS 编译成 WASM**，里外的对象表示根本不是一回事，那类逃逸从原理上不成立。

**推论**：`vm` 模块、`Proxy` 包一层、"我们自己写个受限 runtime" —— 这几种都**不是安全边界**，
只是防呆。真边界只有两种：**进程隔离**（OS 管）或**不同的 VM**（WASM）。

### 3.2 两半各关各的

| 哪一半 | 关在哪 | 它能做什么 |
| --- | --- | --- |
| **A 面（UI）** | `<iframe sandbox="allow-scripts">`（**不给 `allow-same-origin`** → 不透明源）+ CSP `default-src 'none'` | 在自己的矩形里画；只能 `postMessage` 跟我们说话 |
| **B 面（逻辑）** | 独立进程：`ELECTRON_RUN_AS_NODE=1 electron --permission --allow-fs-read=<只给它该看的>` | 算；要碰盘或联网就回调宿主 |

### 3.3 实测读数

**A 面边界**（Chromium 152 / Electron 44）：

| 试什么 | 只有 `sandbox="allow-scripts"` | 加 CSP `default-src 'none'` |
| --- | --- | --- |
| 读父页面 DOM | ❌ SecurityError | ❌ |
| `top.location` | ❌ SecurityError | ❌ |
| `location.origin` | `"null"`（不透明源） | 同 |
| `localStorage` | ❌ SecurityError | ❌ |
| 父页面读它的 `contentDocument` | ❌ `null` | ❌ |
| **`fetch` 外传** | ✅ **能发出去** | ❌ |
| **`<img src>` 带参数外传** | ✅ **能** | ❌ |
| **`sendBeacon`** | ✅ **能** | ❌ |
| **`WebSocket`** | ✅ **能** | ❌ |

> ⚠️ **`iframe sandbox` 单独用不挡网络。** 插件可以靠一张图片的 URL
> 把项目内容偷传出去。**必须配 CSP**，而且 CSP 要下在**响应头**上 ——
> 下在页面里的 `<meta>` 虽然插件也解不开（CSP 只能收紧），但响应头连碰都碰不到。
>
> 这一条差点漏掉：第一版测试对照组也是零，一度以为 CSP 之前就没网络。
> 查出来是父页面用了 `data:` URL（不透明源），Chrome 对这种上下文访问 localhost 另有限制 ——
> **仪器是死的**（纪律④）。换成真实来源后对照组三个请求全部打进来，才量准。

**B 面边界**（Node 24 权限模型，Electron 44 内置 Node 24.21）：

```
$ ELECTRON_RUN_AS_NODE=1 electron --permission --allow-fs-read=/私有/某目录/ probe.js
{"hasPermissionApi":true,"canReadEtc":false,"canSpawn":false,"canNet":false,
 "actuallyReadEtc":false,"err":"ERR_ACCESS_DENIED"}
```

读没放行的路径、起子进程、联网**都被拒**。权限模型 Node 24 起转正，
**在 Electron 的 node 模式下行为一致** —— 这是实测，不是照文档抄。

> 坑一条：macOS 上 `/tmp` 是指向 `/private/tmp` 的符号链接，
> `--allow-fs-read=/tmp/` 放行不了 `/private/tmp/` 下的东西，**连脚本自己都读不了**。
> 放行路径一律用 `realpath` 解过再给。

### 3.4 权限清单在 manifest

插件要什么，写在 manifest 里，**装的时候给用户看一遍**：

```jsonc
{
  "id": "com.umbra.video",
  "surfaces": ["ui", "tools"],           // 两个能力面，没声明的不加载
  "kinds": ["video"],                     // 它认领哪些文件类型
  "hostApi": "^1",                        // 宿主 API 大版本
  "permissions": {
    "files": ["read", "write"],           // 只能通过 host.call 走两条写入口
    "scope": "project",                   // 只看得到当前项目目录，看不到别的项目、看不到用户主目录
    "net": [],                            // 要联网就在这里列域名；空 = 完全不许
    "exec": []                            // 要跑外部程序（比如 ffmpeg）在这里列
  }
}
```

⚠️ **`exec` 这一项是最大的口子。** 视频插件八成要 ffmpeg。
一旦允许起子进程，Node 权限模型那道墙就等于开了个门 —— 子进程不受父进程权限约束。
§九 把它列成待拍板。

## 四、授权：离线可用 + 时效

用户定的：**离线可以使用**、**一次买断**、**购买可以有时效概念**（限时免费、赠送时长）、**插件可更新**。

### 4.1 签名许可证（离线怎么成立）

业界成熟做法，我们照用：

1. 服务端用 **Ed25519 私钥**签一份许可证；签名 64 字节，验证极快
2. 主程序内置**公钥**，本地验签 —— **全程不需要联网**
3. 许可证里写：许可给谁、哪些插件、什么时候起、什么时候止（可为空 = 永久）、绑哪台机器

```jsonc
{
  "sub": "<账号 id>",
  "grants": [
    { "plugin": "com.umbra.video", "from": "2026-09-26", "until": null,        "src": "purchase" },
    { "plugin": "com.umbra.html",  "from": "2026-09-26", "until": "2026-10-26", "src": "promo" }
  ],
  "device": "<机器指纹>",
  "iat": "2026-09-26T…"
}
```

**时效就是 `until`**：买断的写 `null`，限时免费 / 赠送时长的写到期日。
同一套机制同时满足「一次买断」和「方便后期运营」—— 不用两套。

### 4.2 时钟回拨

有时效就有这个问题：用户把系统时间调回去，过期的又能用了。

做法：**单调高水位**。本地记下「见过的最晚时间」，只许前进不许后退；
之后看到更早的时间就判定为回拨。落盘用**先写临时文件再改名**的原子写 ——
半个文件能解析成"时间零"，那这道检查就静悄悄失效了。

**注意它的上限**：这挡的是顺手改时间，挡不住会改文件的人。
**离线授权一定可破解**，这是「离线可用」这个需求自带的代价，不是实现没做好。
真正的防线是三条：① 正版够便宜够方便 ② 更新要联网 ③ 账号绑定，共享许可证 = 共享账号。

### 4.3 「买断」买的是什么 —— 要定

买断 + 插件可更新，就有一个跑不掉的问题：**三年后的大版本还算在里面吗？**

两种常见做法：

| 做法 | 用户感受 | 收入 |
| --- | --- | --- |
| 永久，所有版本 | 最舒服 | 一次性，没有复购 |
| 买断当前大版本，大版本升级可选付费（JetBrains 那类） | 能接受，但要讲清楚 | 有复购 |

〔建议〕**第二种**，且第一期把大版本升级做成「可选」而不是「强制」——
老版本插件继续能用，只是不再更新。许可证里的 `until: null` 配一个
`majorVersion: 1` 就够表达，**现在就把这个字段留出来**，将来不用改格式。

## 五、积分与购买

用户定的：**一次买断制，用积分购买；积分可充值；积分可抵扣插件费用**。
（积分也能抵扣大模型费用，用户明确说**不在本次范围内**，但下面的账本设计要能容下它。）

### 5.1 需要的东西

| 件 | 为什么 |
| --- | --- |
| 账号 | 许可证要绑人，换机器要能恢复已买的东西 |
| 积分余额 | 服务端是**唯一事实**；客户端显示的一律是缓存 |
| 流水账本 | 充值 / 消费 / 退款 / 赠送 每一笔都要有记录，**能对账**。将来大模型扣费也记在同一本账上 |
| 商品表 | 插件 id、价格（积分）、当前版本、更新日志、截图 |
| 订单 | 一次购买一条，不可变；许可证由订单派生 |

### 5.2 几条要写死的规则

- **积分只进不出**：充值进来的积分**不退现金**（要退就退到积分余额）。这条要在充值页写清楚
- **价格变动不影响已买**：买过就是买过
- **余额不足不许赊账**
- **每一笔扣减必须幂等**：客户端网络不稳会重试，重试不能扣两次。订单号做幂等键
- **离线时不能买**：购买必须联网，只有「用」才离线

### 5.3 ⚠️ 合规（需要你确认，我不替你判断）

- **预付值（充值积分）在国内有监管口径**，涉及资金存管、退款、发票、用户协议。
  这一条**必须找专业人士确认**，我只能提醒它存在
- **如果将来上 Mac App Store**，苹果要求数字商品走 IAP 并抽成 30%。
  现在我们是直接下载分发（`.dmg` / `.zip`），不受这条约束 —— **但这也意味着一旦考虑上架，商业模型要重算**
- 未成年人充值、退款争议，需要有处理流程

## 六、分发、安装、更新

### 6.1 装在哪

`STATE_ROOT/plugins/<id>/<version>/`。

**⚠️ 一定是 `STATE_ROOT`，不能是 `TOOL_ROOT`**（`00` §63.1 栽过）：
打包后 `TOOL_ROOT` 在 `.app` 里是**只读**的，而插件要能装、能删、能更新。
这一类缺陷开发模式下测不出来 —— 开发时两个 root 都可写。

### 6.2 装的过程

1. 下载 `.umbraplugin`（就是个 zip）
2. **验签** —— 我们的发布私钥签的包才装。这一步在解压之前
3. 解压到版本目录
4. 读 manifest，**把它要的权限摆给用户看**，用户点同意
5. 注册进插件表；下次打开这种文件就用它

### 6.3 更新

- 新版本装进**新的版本目录**，老版本留着
- 切换是改一个指针 —— **回退只要把指针改回去**
- 只保留最近两版，再老的删掉（不然装几次就占满盘）
- 更新要联网；不更新不影响已装的能用

### 6.4 卸载

删版本目录 + 从插件表摘掉。**插件改过的文件不动** —— 那是用户的东西。
卸载后那种格式退回通用文件卡（`S15`），不是打不开。

用户定的：**第一期只有我自己上架插件可用，后面再考虑开放三方市场**。

**第一期做**：
- 沙箱（两半都做，§三）

- 许可证签发与本地验签（离线）

- **用我们自己的一个真插件走通全程** —— 建议拿 `.md` 或图片这种已经做完的格式
  改造成插件形态，因为它的正确行为我们已经知道，**出问题能一眼看出是插件机制的问题还是功能的问题**

**第一期不做**：
- 三方上架、审核流程、开发者后台
- 插件间互相调用
- 插件卖订阅

**第一期虽然只有自己上架，沙箱照做** —— 理由见 §一 第 4 条。

## 八、对现有架构要改什么

| 条目 | 改什么 | 为什么是前提 |
| --- | --- | --- |
| M11-2 | `FileKind` 从编译期联合类型 → 运行期字符串表 | 插件加的格式，编译期不可能知道 |
| M11-3 | 前端格式注册表支持**迟到注册** | 插件是启动后才装的 |
