# UmbraDesign · 18 方向调研：目录工作台（2026-09-23）

> **这份文件只管一件事：**「UmbraDesign 要不要从『只做设计稿的软件』变成『能打开任意目录、
> 按文件类型给不同预览与编辑方式、AI 对话在侧的工作台』」—— 这个方向的**依据**：
> 竞品实况、需求是否真实、落到我们这里要改什么、能不能做。
> 它是依据出处（和 `04` / `05` / `16` 一类），**不是需求**。待拍板项登记在 `11` §4.2.3（Q18–Q24），
> 定了再改 `01` / `12`。本文不动代码。
>
> 依据标注：【资料】= 公开页面（来源见 §八）；【实见】= 本机仓库里看到的；【判断】= 我的推断，单独标。

---

## 一、要回答的问题

用户 2026-09-23 提出的方向，原话概括：

> 不应该把项目做成只能设计的产品，它本质是一个**能打开目录的编辑器**。
> 主结构不变：左侧对话、右侧选中文件的预览；按选中文件的类型给不同的编辑方式；
> 布局用动态流式，**优先以内容预览为主**。

拆成三问：

| # | 问题 | 答案在 |
| --- | --- | --- |
| A | 市面上有没有人这么做？做到什么程度？ | §二 |
| B | 这个需求是真实存在，还是只是「看起来合理」？ | §三 |
| C | 落到 UmbraDesign 要改什么、能不能做、代价多大？ | §四 – §六 |

## 二、竞品实况

按「和这个方向的距离」分四圈。**圈 1 是同构产品，圈 4 是需求证据**。

### 2.1 圈 1 · 同构：对话在侧 + 本地目录 + 多类型预览【资料】

| 产品 | 时间 | 布局 | 预览什么 | 和我们的关系 |
| --- | --- | --- | --- | --- |
| **Claude Code 桌面版**（改版） | 2026-04-14 | 会话侧栏；「每个面板都能拖放，把终端 / 预览 / diff / 聊天排成你要的网格」；三档显示模式（Verbose / Normal / Summary） | 应用内文件编辑器、diff 查看器、**HTML 与 PDF 在应用内预览**、本地 dev server | 就是「对话 + 目录 + 预览」，但面向开发者，预览类型只到 HTML / PDF |
| **OpenAI Codex app** | 2026-02-02（macOS）/ 03-04（Windows） | 项目 → 线程侧栏；在线程里看 diff、给 diff 加评论；worktree 隔离 | HTML / 图片 / PDF / xlsx / docx | 同上；产物类型更宽 |
| **Google Antigravity** | 2025-11 起 | **两个视图切换**：Editor（看全部代码）/ Agent Manager（只看代理）；Artifacts = 文本 + 图 + 录屏，**可以在截图上圈一块直接给代理留反馈** | 浏览器预览（代理接管时蓝框） | 「按任务切换整套布局」的实例；圈图反馈就是我们方式 ② 的图片版 |
| **Cursor 3.0** | 2026-04-02 | Agents Window 成主界面，IDE 变可选（「可随时切回，或两个都开」）；多聊天并排 / 网格；Design Mode：在浏览器里标注元素发给聊天 | 浏览器预览内嵌 | 编辑器退居次位、对话成主界面，行业方向明确 |
| **「One Claude」** | 2026-09-16 | Cowork + Design + Docs + Slides + Artifacts 并入**同一个对话**；「Claude 自己判断任务需要什么」；Claude Design 单独版「照常可用」 | 文档 / 幻灯片 / 设计 / 网页产物在侧栏 | **参照物本身从『设计专用』变成『对话 + 多种产物类型』**。用户的方向和 Anthropic 一周前的动作是同一个判断 |

一句话：**「左对话、右产物预览、产物类型不限」在 2026 年已经是头部厂商的默认形态**，
差别只在产物存在云端（One Claude）还是本地目录（Claude Code 桌面版 / Codex app）。

### 2.3 圈 3 · 本地知识库 + AI（非代码文件）【资料】

| 产品 | 关键事实 | 说明了什么 |
| --- | --- | --- |
| Obsidian AI 插件群（Copilot / Smart Connections / Smart Composer / Text Generator / Local GPT） | 评测原话：「它们没法把这些上下文给你的其它 AI 工具。这是天花板，而且是结构性的，不是缺个功能」 | 锁在一个 App 里的 AI 是死路；**产物在目录里、任何模型都能接**才是出路（我们的 MCP 出口正是这个） |

## 三、需求是否真实 —— 结论

**有依据的结论：**

1. 「对话在侧 + 本地目录 + 按类型预览」的需求**真实存在，而且已被验证**：
   2026 年 2 月（Codex app）、4 月（Cursor 3.0、Claude Code 桌面版）、9 月（One Claude）
   四次头部产品改版全指向同一形态。这不是要不要去验证的事，是**大厂正在收割**的事。
2. 但需求要按人群拆开，三类人的处境完全不同：

| 人群 | 现状 | 缺口 | 我们该不该碰 |
| --- | --- | --- | --- |
| 开发者 | Cursor / Codex app / Claude Code 桌面版已经满足 | 无 | **不碰**。做代码 IDE 必输 |
| 写作 / 笔记（md 目录） | 两头夹着：凑合用 Cursor（没预览）或 Obsidian 插件（锁在 App 里） | 真实：**要预览 + 要 AI + 不要被锁** | 可以顺手覆盖（md 是最便宜的类型），但付费意愿弱（这一圈全免费） |
| 设计 | Claude Design（云）/ pen.dev（本地画布）/ Onlook（转云） | 本地 + 开放格式 + 语义变更交付，目前只有我们 | **核心不变** |

3. 对 **UmbraDesign 自己的使用者**（`01` §二）来说，目录工作台的价值是具体的，不是抽象的：
   - 实现侧要在同一窗口里看 `.dc.html` 和 `CHANGELOG-设计侧.md`，今天做不到（md 没有预览）；
   - 设计项目目录里**本来就有**非稿文件：`project.json`、`_ds/` 下的 tokens、`uploads/` 里的图、评论 json ——
     今天它们在应用里是不可见的；
   - **秘书**（`umbrapc`）要接的是「用户的任意文件」，不只是设计稿；泛型的目录 / 文件能力是接入前提。

**判断（不是结论）：**
需求成立的是**「工作台」形态**，不成立的是**「通用编辑器」**。
工作台 = 一个目录、所有文件都能看、少数类型能改、AI 对什么都能说；
通用编辑器 = 每种类型都做到专业工具的深度 —— 后者做不到，也没必要，
而且和 `01` §八「不做通用网页编辑器」的精神一致。

## 四、落到 UmbraDesign：产品定义怎么变

### 4.1 定义句的变化（若 Q18 采纳）

| | 现在（`01` §一） | 提案 |
| --- | --- | --- |
| 定义 | PC 端**设计软件** | 跑在自己电脑上的**目录工作台**：打开一个目录，左边和 AI 对话，右边看选中的文件；**设计（`.dc.html`）是它最深的一种文件类型** |
| 判据 | 「做一个和 ClaudeDesign 基本一样的软件，最大不同是设计稿存本地」 | 「做一个和 One Claude 里『对话 + 产物』基本一样的工作台，最大不同是**产物在你的目录里，任何模型都能接**」 |
| 不变 | 三种编辑方式、`.dc.html` 格式、唯一写入口、语义 diff、断网、MCP 出口 | 全部不变 —— 这些是设计类型的深度，不是被替换的东西 |

**和 `01` §八 不冲突的地方**：仍不做自由画布、仍不做通用 DOM 编辑、仍不做云同步。
**要改的**：§一 定义、§二 使用者（加「任何要和自己目录里的文件对话的人」）、
§四 加一节「文件类型矩阵」、§八 加一行「不做代码 IDE」。改法按 `11` Q10：整段改，不留旧说法。

### 4.2 文件类型矩阵（预览 × 三种编辑方式 × 可行性）

标注可行性：**能做** = 现有栈直接做；**能做·要 vendor** = 断网约束 H2 要求把库打进 `runtime/`；
**可以级** = 能做但不值得第一批；**不做**。

| 类型 | 预览 | ① 手动改 | ② 选中 → AI | ③ 对话 | 可行性 |
| --- | --- | --- | --- | --- | --- |
| `.dc.html` | S2 编辑壳 | 属性面板 | 节点桥 | ✅ | **已有**（M0–M6） |
| 目录 | 列表 / 缩略图网格（S1 稿件索引泛化到所有文件） | 新建 / 改名 / 移动 / 删除（生命周期已有，泛化到非稿） | 选中若干文件当上下文 | ✅ | **能做**：S1 与生命周期工具泛化 |
| `.md` | 渲染视图 + 源码视图切换 | 源码编辑器（所见即所得是第二步） | 选中段落 → AI | ✅ | **能做·要 vendor**：markdown 渲染器 + 文本编辑器（CodeMirror 6 量级，约 300 KB） |
| `.html`（非 dc） | iframe，走本地 http（H1） | 无（只读） | 点选元素带 `outerHTML` 给 AI | ✅ | **能做**；【判断】点选桥要为非 dc 页面单独注入一版，需验证 |
| 图片 png / jpg / svg / gif / webp | 原生 `<img>`，缩放 | **不做**（不做图像编辑） | **圈一块区域 + 一句话 → AI**（Antigravity 式） | ✅ | **能做**；多模态见 §4.4 |
| 代码 / 文本（ts / js / json / css / yaml / txt） | 只读高亮 | 允许改字面量，**不做 IDE 功能**（无补全 / 终端 / 调试） | 选中行 → AI | ✅ | **能做·要 vendor**（和 md 共用编辑器） |
| `.pdf` | 视图 | 无 | 无（第一批） | 文本抽取后可对话 | **可以级**：macOS WKWebView / Windows WebView2 原生能渲染 PDF，Linux 要 pdf.js（约 2 MB） |
| docx / xlsx | 转 HTML 只读（mammoth / SheetJS） | 无 | 无 | 转文本后可对话 | **可以级** |
| pptx | — | — | — | — | **不做** |
| 其它二进制 | 元数据卡（大小 / 时间 / 类型 / 哪些稿引用了它） | 改名 / 移动 | — | — | **能做** |

### 4.3 布局：动态流式，预览优先

提案规则（R1–R5），供拍板（Q20）：

| # | 规则 | 理由 |
| --- | --- | --- |
| R1 | **预览区永远是最大面板**；其它面板按「当前文件类型需要什么」出现：`.dc.html` 出属性 / 诊断 / 变更，`.md` 出大纲，图片什么都不出 | 用户原话「优先以内容预览为主」；Antigravity「按任务换整套布局」的本地版 |
| R2 | 会话栏可左可右、可**收成一条输入条**；收起时预览吃满 | M6-1 已有开关，只加一档「收成条」 |
| R3 | 第一阶段**不做自由拖拽网格**（Claude Code 桌面版那种）；做「按类型预设 + 可收起 + 记住每种类型上次的收放状态」 | 自由网格的状态持久化 / 恢复 / 边界情况是一大块工作；单人用，预设够 |
| R4 | 切换文件时只换**从属面板**，左栏与预览的分界线不动 | 避免每点一个文件整屏跳 |
| R5 | 窗口宽 < 1100 px 时从属面板改抽屉 | Tauri 窗口可能很小 |

**【判断】前置工程**：现在应用前端是**一个 1,729 行的 vanilla `index.html`**（`server/ui/`，124 KB）【实见】。
再塞 4–6 种预览器和一套动态布局，会过可维护上限。建议在动布局前引入构建（Vite，按文件类型拆模块），
这是工程前置，不是需求，登记为 Q21。

### 4.4 AI 侧的变化

| 项 | 现在 | 变化 |
| --- | --- | --- |
| 会话绑定 | 绑项目 | 不变 |
| 方式 ② 的「选中对象」 | 节点 | 泛化为：节点 / 文本区间 / 图片区域 / 文件 / 目录 —— 会话里的「已选中药丸」显示类型 |
| 写入 | 唯一写入口 `write_draft`（dc 专用链：归一化 → `@ds` → `__resources` → 节点地址 → 快照 → changelog） | 非 dc 文件**不能走这条链**（链里每一步都是 dc 语义）。要一条泛型写入口：写前 sha256 校验（Q8 已定）+ 简单快照；**语义 diff 只对 `.dc.html`**。版本纪律怎么定见 Q22 |
| MCP 工具 | 27 个，全是 dc 专用【实见】 | 加泛型：`list_files` / `read_file` / `write_file` / `move_file`（复用生命周期）。**这是秘书接入的必要条件**（Q23） |
| 多模态（图片 → AI） | 通道 A 走 OpenAI Chat Completions 形状 | **可以做**【资料】：DeepSeek 2026-08-21 发了 `deepseek-v4-flash-vision-exp`，OpenAI 兼容、支持 base64 / URL 图片、支持工具调用、每图 ≤ 384 token、标「实验性」；智谱视觉模型同样 OpenAI 兼容。模型名本来就由用户配（`01` §六），只需在配置里给通道标一个「支持图片」开关（Q24） |

### 4.5 明确不做（提案，进 `01` §八）

| 项 | 为什么 |
| --- | --- |
| 代码 IDE：补全 / 终端 / 调试 / git 面板 | §三：开发者已被满足，做了必输 |
| 图像 / PDF 编辑 | 只看、只圈、只对话 |
| 自由画布、云同步、多人、Share | 不变（`01` §八） |
| 每种类型做到专业深度 | 工作台不是通用编辑器（§三判断） |

## 五、差异化一句话

| 对手 | 它 | 我们 |
| --- | --- | --- |
| One Claude | 产物在 Anthropic 云端，只有 Claude 能改 | 产物在你的目录里，**任何模型**通过 MCP 都能改 |
| Claude Code 桌面版 / Codex app | 为代码而生，预览是附属 | 为**产物**而生，预览是主面板 |
| pen.dev | 画布式，私有 `.pen` | 文档式，开放 `.dc.html` + 四级语义 diff + 变更清单 |
| Obsidian + 插件 | AI 锁在 App 里 | 目录即作用域，AI 可换、可外接 |

## 六、风险与代价

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| **范围膨胀** | 每加一种类型 = 预览器 + 选中桥 + 写入路径 三件套 | 每期只加一种类型，每种有验收用例（对照 `01` §七的口径） |
| **前端重构** | 4.3 的【判断】：单文件 vanilla 撑不住 | Q21 先定；不定就别动布局 |
| **写入纪律分叉** | dc 有语义快照，别的文件没有 —— 用户看到两套「版本」口径 | Q22 定一种说法，界面上明示「这类文件只有快照没有语义 diff」 |
| **定位稀释** | 一旦叫「工作台」，会有人拿它和 Cursor 比 | `01` §八 写死「不做代码 IDE」；首页 / README 第一句仍强调设计 |
| **秘书边界** | 秘书是否直接用这个工作台当文件面，决定泛型 MCP 工具的优先级 | Q23 |
| 圈 4 证据偏开发者社区 | 五篇「Cursor + Obsidian」作者都是技术人 | 【判断】我们的使用者本来就是设计侧 / 产品侧 / 实现侧，偏差可接受 |

## 七、对分期的影响（只提方向，排期归 `11`）

- 不打断 M6 / 通道 B 收尾。
- 若 Q18 采纳：新开 **M7 工作台**，建议顺序：Q21 构建前置 → 目录视图泛化 → `.md` → 图片（含圈选 → AI）→ 泛型 MCP 工具 → 代码 / html 只读。
- `.pdf` / docx / xlsx 不排进 M7。
