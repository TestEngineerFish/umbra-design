# UmbraDesign · 11 产品定位与路线图

> 这一份是 2026-09-19 的**重新定位**。在它之前，`01`～`10` 把 UmbraDesign 当成
> 「给大模型用的本地 MCP 工具」来写；现在明确：**UmbraDesign 是一个 PC 端设计软件**，
> MCP 只是它的一层内部能力。
>
> 老文档不废：`00` 是工具契约、`02`/`03` 是格式与运行时语义、`06` 是写稿规则、
> `07` 是变更交付 —— 这些都还成立。变的是**产品边界**和**谁在用**。
>
> 待办与进度见 `12-待办清单.md`。需要拍板的问题集中在本文件 §八。

## 一、这是什么

**一个跑在自己电脑上的设计软件。** 能创建和管理设计项目，能编辑设计稿，
而设计稿就是 `.dc.html` —— 一份文件同时是设计稿、规范出处和可运行原型。

参照物是 **ClaudeDesign**。判据很直接：

> **做一个和 ClaudeDesign 基本一样的软件，最大的不同是设计稿存本地。**

「存本地」不是一句实现细节，它决定了一串东西：项目就是磁盘上的一个目录、
版本就是本地快照（`.umbradesign/snapshots/`）、变更清单是仓库里的一个 Markdown、
断网必须可用、稿件双击（或本地 http）就能打开给实现侧看。

### 1.1 三种编辑方式（照 ClaudeDesign）

| # | 方式 | 谁在改 | 一次交互的形状 |
| --- | --- | --- | --- |
| ① | **手动选中元素编辑** | 人，直接改 | 在预览里点一个元素 → 改数字 / 挑颜色 / 改文案 → 稿变了 |
| ② | **选中元素后发消息给 AI** | 人指位置，AI 改内容 | 点一个元素 → 在会话里说「这里改成 X」→ AI 改 → 人看结果 |
| ③ | **直接与 AI 对话** | AI 全程 | 说需求 → AI 读规则与取值 → 写稿 → 校验 → 体检 → 回报变更 |

三条都必须在**同一个应用窗口里**完成 —— 这是 ClaudeDesign 的形状，
也是和「今天这版」最大的差别：今天 ② 和 ③ 要在另一个应用（Claude Code / Codex）里做。

### 1.2 谁在用

| 使用者 | 用来干什么 |
| --- | --- |
| **设计侧**（主） | 建项目、写稿、调形制、看变更 —— 三种方式都用 |
| 产品侧 | 看稿、看状态清单、提改动（走 ②③） |
| 实现侧 | 打开稿取值、读 `CHANGELOG-设计侧.md` —— **只读** |
| Umbra 秘书 | 后续接同一套能力（第二阶段，见 `01` §二） |

⚠️ `01` §二 写的「第一阶段调用方是模型，不是人」**已经过期**。
那是 MCP-only 阶段的取舍。现在人是第一使用者，模型是人的一种工具。

## 二、和 ClaudeDesign 的对照

### 2.1 一样的

- 设计稿格式：`.dc.html`（`<x-dc>` 模板 + `data-dc-script` 逻辑类），运行时是同一份
  `support.js`（69 KB，未压缩，**原样 vendor，不重写** —— 依据见 `05`）
- 三种编辑方式（§1.1）
- 一份文件里放多种状态，可切换地存在，而不是散成十几张图
- 组件复用走 `dc-import`；设计系统走 token / 图标检索

### 2.2 不一样的（我们的选择）

| 维度 | ClaudeDesign | UmbraDesign |
| --- | --- | --- |
| 稿件存储 | 云端 | **本地目录**，一个项目一个目录 |
| 版本 | 云端历史 | 本地语义快照 + 可选 git 兜底（`07` §七） |
| 变更交付 | — | `CHANGELOG-设计侧.md` + 四级语义 diff（L1 契约 / L2 取值 / L3 文案 / L4 等价） |
| 离线 | 需要网络 | **断网必须可用**（React 与运行时都 vendor 在本地） |
| 校验 | — | 落盘即静态校验 + 真浏览器渲染体检，诊断带行号 / 洞名 / 改法 |
| 对外能力 | — | 同一套能力同时暴露成 **MCP server**，别的模型客户端可以直接连 |
| 样式差异 | — | 皮肤是我们自己的一套（`ui/_ds-tool/tokens.css`），不追求像素级一致 |

### 2.3 我们多出来的那部分，不是附加功能

四级语义 diff、渲染体检、`CHANGELOG-设计侧.md` 这三件，是本地存储**换来的**：
稿在本地、版本在本地，才有可能对任意两版做语义比对并把结论写成一份实现侧能读的文件。
它们是这个产品和「一个画图工具」的分界线，优先级不低于编辑能力本身。

## 三、项目与稿件的完整生命周期

这是当前最大的缺口。今天的能力只覆盖了中间一段（「改」），两头几乎是空的。

### 3.1 项目

```
新建 → 配置（设计系统 / 限额）→ 打开 / 切换 → 改 → 归档 / 删除
                                      ↑
                                导入已有目录
```

| 环节 | 今天 | 要做 |
| --- | --- | --- |
| 新建 | ❌ 手写 `project.json` | 建目录 + 配置 + `.gitignore` + 第一份稿 |
| 导入已有目录 | ⚠️ 放进 `projects/` 就算 | 任意路径 + 最近项目列表（见 §八 Q5） |
| 打开 / 切换 | ⚠️ 命令行传名字 | 界面里选，记住最近打开 |
| 配置 | ❌ 手改 JSON | 项目设置页 |
| 归档 / 删除 | ❌ 无 | 需要，且要先回答「删了会影响谁」 |

### 3.2 稿件

```
新建（空白 / 模板 / 复制 / 从组件）→ 改 → 改名 / 移动 / 复制 → 删除（回收站）
                                      ↓
                              版本快照 · 变更清单 · 体检读数
```

| 环节 | 今天 | 要做 |
| --- | --- | --- |
| 新建 | ❌ 无（只能由模型 `write_draft` 写全文） | 空白骨架 / 模板 / 复制一份 / 把组件包一层 |
| 改（①） | ✅ 已通 | — |
| 改（②③） | ⚠️ 要另一个应用 | 应用内会话 |
| 改名 | ❌ 无 | **且必须同步改所有 `dc-import name="…"` 的引用** |
| 移动 / 分组 | ❌ 无 | 同上，引用要跟着修 |
| 复制 | ❌ 无 | 要 |
| 删除 | ❌ 无（第一批刻意排除，怕误删） | 回收站语义（见 §八 Q4），删前查引用 |
| 版本 / 变更 / 体检 | ✅ 已通 | — |

### 3.3 一个必须先解决的问题：引用完整性

`dc-import name="IconGlyph"` 是**按文件名解析**的。所以改名、移动、删除任何一份
被别人引用的稿，都会静默打断引用 —— 而 `E_IMPORT_MISSING` 只在下次校验时才报。

所以生命周期的第一件事不是 CRUD，是**「谁引用了我」**这个查询：
改名和移动要能连带修引用，删除要能在动手前说清影响范围。

## 四、架构：今天有什么，要加什么

### 4.1 今天（已经跑通的）

```
┌─ 界面（浏览器）: S1 索引 · S2 预览壳+属性面板 · S3 诊断 · S4 变更 · S5 设计系统 · S7 形制稿
│      ↕ 本地 JSON API（/__ud/*，随机令牌 + Origin 校验）
├─ 本地静态服务（127.0.0.1，随机端口）
├─ 核心层: 写入口 / 校验 / 渲染体检 / 语义快照与 diff / 节点地址 / 属性级写入 / 回退
└─ MCP server（stdio，27 个工具）——  外部模型客户端从这里接
```

启动方式两条：`npm run ui`（人）· MCP 注册（模型）。

### 4.2 要加的三块

**① 生命周期能力层** —— 项目与稿件的 CRUD + 引用完整性。
既要暴露成 MCP 工具（模型也要能建稿），也要在界面上有入口。

**② 应用内 AI 会话** —— 方式 ②③ 的落点。它需要：
一个会话模型、一个能调我们自己 27 个工具的 agent 循环、
改动前的预览与确认、以及和 `revert_to` 打通的一键回退。
**大脑从哪来是个待定项**（§八 Q2）。

**③ 应用外壳** —— 窗口、菜单、最近项目、文件夹选择、进程管理、打包分发。
选型待定（§八 Q3）。

⚠️ **刻意的顺序**：外壳放在最后，因为在它出现之前，`npm run ui` + 浏览器
已经是一个完整可用的形态，每一期都能真测；而外壳是包装，它需要先知道里面装什么。
这一条我拿不准，列进 §八 Q1。

### 4.3 一条不变的原则

**唯一写入口。** 所有落盘都走 `write_draft` 那条路（归一化 / `@ds` 展开 /
`__resources` 注入 / 节点地址 / 快照 / changelog）。新增的生命周期能力、
AI 会话、界面编辑，一个都不例外。这条规矩在第一批救过好几次（`00` §十五）。

## 五、分期路线图

每一期都以**「能不能真测」**为界，不以代码量为界。

| 期 | 名字 | 一句话 | 验收怎么测 |
| --- | --- | --- | --- |
| **M0** | 已完成 | 稿件能被安全地写、校、体检、比对；界面能看能改单个属性 | 见 `12` §一，已全部验收过 |
| **M1** | 生命周期 | 从零建项目、建稿、改名、复制、移动、删除，全程只用界面 | 空目录起步，建 1 个项目 + 3 份稿（含一个被引用的组件），改名一次、移动一次、删一次、回收站恢复一次；期间 `dc-import` 引用不断，`selftest` 零误报 |
| **M2** | 应用内 AI | 方式 ②③ 在应用里完成 | 在应用里说「把这个按钮改成 danger 态」→ 稿变了、S4 出 L1–L4 分级、一键回退能退回去；选中一个节点说「这里字号大一点」→ 只有那一处变 |
| **M3** | 应用外壳 | 双击图标就能用，不碰终端 | 打包出的应用里：新建项目 → 建稿 → 改 → 关掉重开，最近项目在，稿还在 |
| **M4** | 画布与对比 | 看得更清楚 | S6 并排看两版差异并高亮；组件稿改 props 实时重渲染；多宽度预览 |
| **M5** | 打磨 | 全局搜索、设计系统编辑、并发与恢复 | 逐条见 `12` §六 |

**为什么 M1 在 M2 前面**：没有建项目和建稿，AI 会话没有可作用的对象 ——
今天连「新建一份空白稿」都只能由模型写全文，那不是产品。
**为什么 M2 在 M3 前面**：三种编辑方式是这个产品的定义，外壳是包装。
在浏览器里跑的 M2 已经可以每天用。

## 六、每一期的「可测试」是什么意思

不是「跑起来没报错」，是**有一条能复述的读数**：

- M1：一条脚本化的生命周期回归（建→改名→移动→删→恢复），
  每一步之后跑 `validate_draft`，引用必须仍然解析得开。加进 `fixtures/`。
- M2：一组**固定提问**对固定稿的回归。不判断 AI 的措辞，只判断三件事：
  改动落在了对的节点上、四级分级对、回退能退回去。
- M3：打包产物在一台干净机器上走一遍首次使用流程。
- M4/M5：各自的读数见 `12`。

## 七、明确不做

| 项 | 为什么 |
| --- | --- |
| 重写 `support.js` | 引擎已经有了，原样 vendor（`05`）。改它等于接管一个 69 KB 的运行时 |
| 云端同步 / 账号 / 协作 | 「存本地」是产品定义的一部分，不是过渡形态 |
| 像素级复刻 ClaudeDesign 的皮肤 | 形制照它，配色和密度用我们自己那套 token |
| 通用网页编辑器 / 自由画布 | 我们编辑的是 `.dc.html` 的结构与取值，不是任意 DOM |
| `bundle_draft`（内联单文件，形态 B） | 两点仍未验证，从第一批起就没承诺（`00` §九） |
| 导出 PDF / 切图 | 交付物是稿本身 + 变更清单，不是图片 |
