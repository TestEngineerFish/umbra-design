# UmbraDesign · 08 工具界面设计需求

> **这一份是交给 Claude Design 的设计委托单。**
> 它定**要画哪些屏、每屏有哪些数据和状态、有哪些技术约束**；
> **不定视觉** —— 视觉请沿用你自己的界面语言（见 §一末）。
>
> 读这一份不需要先读 00–07，需要的数据形状都内联在这里了。

---

## 一、背景

UmbraDesign 是一个**本地 MCP server**，功能与 Claude Design 基本重合：
让大模型写 `.dc.html` 设计稿、校验、渲染体检、把变更讲清楚给实现侧。
格式与运行时沿用现有的那一套（`x-dc` 模板 + `{{ 洞 }}` + 逻辑类 + `support.js`）。

区别只有两点，但影响界面：

1. **第一阶段的调用方是大模型，不是人。** 所以界面不是主入口，
   是**人要看的那几个面**：稿子有哪些、这一份画对了没有、这一轮改了什么。
2. **它是工具，要分发给别人用。** 设计系统是可插拔的项目输入，
   Umbra 只是第一个项目。**界面不能长成 Umbra 的样子。**

现在这个项目一点样式都没有，需要一整套。

> ### 关于视觉
>
> 写这份单子的人看不到 Claude Design 的界面，所以这里不写任何视觉规定。
> **请沿用你自己那一套界面语言**：布局骨架、间距节奏、字阶、控件形态、
> 缩略图墙的排布、状态徽章的形状、空态的写法。功能几乎一样，形态可以直接搬。
>
> 唯一必须换掉的是**色板** —— 理由见 §2.4。

## 二、技术约束（这几条决定了能画什么，请先读）

### 2.1 界面自己也用 `.dc.html` 写

工具界面用它自己要处理的格式来写 —— 自举。好处是不引入第二套技术、
复用同一个 `support.js`、顺便验证框架。

所以 §三的每一屏都是一份 `.dc.html`：`x-dc` 模板 + `{{ 点号路径 }}` 洞 +
`<sc-if>` / `<sc-for>` + 一个 `Component extends DCLogic` 逻辑类。

### 2.2 语法与写法约束

| 项 | 规则 |
| --- | --- |
| 洞 | **只能是点号路径**。`{{ a + b }}`、`{{ fn() }}` 一律不支持，要算就在 `renderVals()` 里算好 |
| 样式 | 一律写在 `style` 属性上。例外只有 `@font-face` / `@keyframes` / body 重置，放 `<helmet>` |
| 逻辑 | 经典 JS，无 `import` / `export` / TS。`renderVals()` **同步**，返回扁平对象 |
| 依赖 | 无构建、无 npm。React 走租户目录里的本地副本 |
| 规模 | **一份稿 ≤ 1,200 个静态元素标签。** 超了就拆成多份 |
| 打开 | 走本地 http（不是双击）。所以 `dc-import` 可用，放心拆组件 |
| 动画 | 只有 `.12s–.15s ease` 的颜色 / 描边过渡和开关位移；运行中用匀速旋转。**不做弹跳、缩放、入场动画** |

### 2.3 ⚠️ 预览区必须是 iframe

单稿预览（S2）里，被预览的稿子**不能直接嵌进壳的 DOM**。两个原因：

1. 稿子的 `<helmet>` 会把 `--bg` / `--text` / `--card` 这一类变量注入 `:root`，
   **壳如果用同名变量会被污染**；
2. 稿子有自己的 body 重置。

所以：**被预览的稿子放 `<iframe>`**，壳与稿子各跑一份 `support.js`，互不干扰。
壳需要知道稿子的尺寸时用固定视口档位（见 S2 的状态清单），不做自动撑高。

### 2.4 ⚠️ 工具皮肤的 token 一律 `--tool-` 前缀，且不能用 Umbra 的色板

`--tool-bg` / `--tool-panel` / `--tool-border` / `--tool-text` / `--tool-muted` /
`--tool-accent` / `--tool-ok` / `--tool-warn` / `--tool-err` / `--tool-hover` …

两条理由：

- **防污染**：即便有了 iframe，壳与稿子仍可能在同一文档里同时出现（诊断面板嵌在预览页里），
  前缀是双保险；
- **防撞身份**：Umbra 是暖灰 + 橙（`#DEDBD5` / `#E8590C` 那一套），那是**某个租户的**
  设计系统。工具界面用它，等于让工具冒充租户。第二个客户进来会很难看。

请给一套**中性的工具皮肤**，浅色 + 深色两份 token 一次给全
（切换功能是第二阶段，但 token 现在就要定，免得回头补）。

### 2.5 不要浏览器原生弹窗

`alert` / `confirm` / `prompt` 会阻塞主线程，让整个页面失去响应。
要确认就用页内的确认条或行内二次确认。

### 2.6 键盘可用

这是工具而不是展示页，键盘路径要通：
列表上下键移动、`Enter` 打开、`Esc` 关闭浮层、`/` 聚焦搜索、`⌘K` 全局跳转（可选）。
每个可聚焦元素要有明确的 focus 态（不要只靠浏览器默认描边）。

## 三、要画的屏

七屏。**S1–S5 是第一批，S6–S7 是第二批**，但第二批的 token 和控件形态
请在这一轮一起定好。

每屏都给了数据形状（真实形状，不是示意）和状态清单。
**状态必须在同一份稿里可切换地存在** —— 页头放一颗小胶囊钮切演示态，
不要散成多张图。

---

### S1 稿件索引（入口页）· 第一批 · 最重要的一屏

**用途**：打开一个设计项目后看到的第一屏。列出这个项目所有的稿，
能搜、能筛、能点进去。这一屏由工具自动生成（扫目录 + 渲染体检的缩略图）。

**数据**：

```json
{
  "project": { "name": "umbra", "title": "Umbra 私人 AI 助手", "draftCount": 27,
               "generatedAt": "2026-09-17T08:52:00+08:00",
               "limits": { "elementsWarn": 1200, "elementsHard": 1500 } },
  "drafts": [
    {
      "file": "日志.dc.html",
      "title": "日志",
      "kind": "page",
      "elements": 812,
      "version": "v217",
      "updatedAt": "2026-09-17T08:40:12+08:00",
      "thumb": ".umbradesign/shots/日志@1440x900.png",
      "health": "ok",
      "diagnostics": { "errors": 0, "warnings": 2 },
      "renderMs": 1840,
      "nodeCount": 2307,
      "states": ["默认", "空日志", "加载中", "失败", "权限不足"],
      "importedBy": ["Umbra PC 端.dc.html"],
      "imports": ["../Components/窗口骨架", "PC 空态"]
    }
  ]
}
```

- `kind`：`page`（页稿）| `component`（组件稿）—— 两者要能区分，组件稿通常是被复用的。
  判据按 import 图定：被别的稿引用 → 组件稿；引用了别的稿 → 页稿；孤立稿看有没有 props（`00` §14.7）
- `health`：`ok` | `warn` | `error` | `unchecked`（还没跑过渲染体检）
- `states`：这份稿里可切换的演示态清单，从模板里抽出来的
- `limits`：租户配的元素数阈值。**页面上的「接近上限 / 已超限」文案要读这两个数，不要写死 1,200**
- `version` / `renderMs` / `nodeCount` 可能是 `null`（没落过盘 / 没跑过体检），页面要有占位形态

**要有的东西**：缩略图墙 + 列表两种视图（工具场景下列表更常用，别只给墙）；
搜索；按 `kind` / `health` 筛；按更新时间 / 元素数排序；
每一项要能看到元素数与健康状态（元素数快到 1,200 要给提示，那是拆稿的信号）。

**状态清单**：

| # | 态 |
| --- | --- |
| 1 | 正常（20+ 份稿，墙视图） |
| 2 | 正常（列表视图） |
| 3 | **空项目**（一份稿都没有）—— 要有引导 |
| 4 | 搜索无结果 |
| 5 | 缩略图还没生成（`unchecked`，占位） |
| 6 | 某几份稿有 error / warning |
| 7 | 某份稿元素数超限（要提示拆分） |
| 8 | 项目配置读不到（`project.json` 缺失或不合法） |
| 9 | 稿很多（100+）时的密度 |

### S2 单稿预览壳 · 第一批

**用途**：打开一份稿。壳提供的是稿子本身没有的东西：它是哪一版、多大、
画得对不对、有没有诊断、换视口、重跑体检、在新窗口打开。

**数据**：S1 里单个 `drafts[]` 项 + 下面这些：

```json
{
  "viewport": { "w": 1440, "h": 900, "preset": "PC" },
  "presets": [
    { "name": "PC",   "w": 1440, "h": 900 },
    { "name": "笔记本", "w": 1280, "h": 800 },
    { "name": "iPhone", "w": 390,  "h": 844 },
    { "name": "自适应", "w": null, "h": null }
  ],
  "zoom": 1,
  "lastCheck": { "at": "2026-09-17T08:41:00+08:00", "alive": true, "renderMs": 1840, "nodeCount": 2307 }
}
```

**要有的东西**：顶栏（稿名、`kind`、版本、元素数、健康徽章、回索引）；
视口档位切换 + 缩放；重跑体检；在新窗口打开原稿；诊断入口（S3）；变更入口（S4）。
**预览区是 iframe**（§2.3）。

**状态清单**：

| # | 态 |
| --- | --- |
| 1 | 正常（体检通过） |
| 2 | 体检进行中（运行中动画用匀速旋转） |
| 3 | 体检失败：`alive: false`（页面卡死）—— 这一态要醒目，它是最坏的结果 |
| 4 | 有 error 诊断 |
| 5 | 只有 warning |
| 6 | 从没跑过体检 |
| 7 | 稿文件不存在 / 被删了 |
| 8 | 窄窗口（壳本身被压窄时怎么退化） |
| 9 | 自适应视口 |

### S3 诊断面板 · 第一批

**用途**：把校验与渲染体检的结果给人看。**这一屏的读者其实主要是模型**
（它拿到的是 JSON），但人也要能看，尤其是要判断"这一条该不该管"。

**数据** —— 这是工具的统一诊断结构，形状固定：

```json
{
  "ok": false,
  "stats": { "elements": 812, "holes": 143, "imports": 4 },
  "errors": [
    {
      "code": "E_HOLE_UNRESOLVED",
      "level": "error",
      "file": "日志.dc.html",
      "line": 128,
      "col": 34,
      "locator": { "kind": "hole", "name": "onRetry" },
      "message": "模板第 128 行的洞 \"onRetry\" 在 renderVals() 的顶层键里找不到",
      "fix": "在 renderVals() 的每一条返回路径里补 onRetry: P.onRetry ?? NOOP"
    }
  ],
  "warnings": [
    { "code": "W_ELEMENTS_WARN", "level": "warning", "file": "日志.dc.html",
      "locator": { "kind": "key", "name": "elements" },
      "message": "812 个元素，接近 1,200 的建议上限",
      "fix": "按顶层 section 或 dc-import 边界拆分" }
  ],
  "render": {
    "alive": true, "nodeCount": 2307, "renderMs": 1840,
    "unresolvedHoles": [{ "name": "onRetry", "line": 128 }],
    "consoleWarnings": [],
    "missingResources": ["_ds/…/tokens/ios.css"],
    "styleSheets": [{ "href": "colors.css", "rules": 2 }]
  }
}
```

**关键**：每条诊断都有 `code`（稳定标识）、定位（文件 + 行号 + 洞名/标签名）、
一句人话、**和一条改法建议**。`fix` 是给模型看的，但人也会照着做，要能一眼读到。
`line` / `col` 可能缺失（定位不到时工具不许瞎填），**缺失态要画**。

**状态清单**：

| # | 态 |
| --- | --- |
| 1 | 全绿（0 error 0 warning）—— 空态要让人放心，别画成"没有数据" |
| 2 | 只有 warning |
| 3 | 有 error（落盘被拒） |
| 4 | error + warning 混合，几十条（要分组、要能折叠） |
| 5 | 某条诊断没有 `line`（定位不到） |
| 6 | 某条诊断没有 `fix` |
| 7 | `render.alive: false` —— 页面卡死 |
| 8 | 有 `missingResources`（资源 404） |
| 9 | 校验跑了但渲染体检没跑 |

### S4 变更清单 · 第一批

**用途**：设计侧改了稿，让实现侧一眼看出**要不要动代码**。
这是这个工具最省时间的一块，优先级和 S1 一样高。

变更分四级，**分级的唯一目的就是回答"要不要动代码"**：

| 级 | 名字 | 实现侧动作 |
| --- | --- | --- |
| L1 | 契约 | **必须改代码**（props / 状态分支 / 事件名 / 子组件引用变了） |
| L2 | 取值 | 照抄新值（颜色 / 间距 / 字号 / token 引用） |
| L3 | 文案 | 改字符串 |
| L4 | 等价 | 无需处理（渲染等价的重排）—— **默认折叠** |

**数据**：

```json
{
  "file": "日志.dc.html", "from": "v216", "to": "v217",
  "counts": { "L1": 2, "L2": 5, "L3": 3, "L4": 2 },
  "changes": [
    { "level": "L1", "kind": "prop_added", "target": "onRetry", "to": "() => void",
      "at": "L45", "message": "新增 props onRetry: () => void",
      "impact": "实现侧需要接这个回调" },
    { "level": "L1", "kind": "branch_added", "target": "hasFailed", "at": "L128",
      "message": "新增状态分支 filter = 'failed'" },
    { "level": "L2", "kind": "style_changed", "target": "日志行", "prop": "line-height",
      "from": "20px", "to": "22px", "at": "L131" },
    { "level": "L2", "kind": "token_changed", "target": "失败态底色",
      "from": "var(--danger-soft)", "to": "var(--warning-soft)", "at": "L136" },
    { "level": "L3", "kind": "text_changed", "target": "空态标题",
      "from": "暂无日志", "to": "这段时间没有日志", "at": "L96" },
    { "level": "L4", "kind": "reordered", "target": "2 处容器重排" }
  ],
  "spans": ["v217"]
}
```

`spans` 在跨版本合并时会有多项（"我在 v217，现在 v221"），要能显示跨了哪几版。

**要有的东西**：按级分组；L4 默认折叠；取值级要**并排显示旧值 → 新值**
（颜色变更最好带色块）；每条能跳到行号；整个清单能一键复制成纯文本
（实现侧可能要贴到工单里）。

**状态清单**：

| # | 态 |
| --- | --- |
| 1 | 四级都有 |
| 2 | **只有 L4**（这一版其实什么都没改）—— 要说清楚"不用管" |
| 3 | 只有 L1（纯契约变更，最需要醒目） |
| 4 | 无变更（两版完全相同） |
| 5 | 跨多版合并（`spans` 有 4 项） |
| 6 | 变更很多（80+ 条） |
| 7 | 整个项目级的清单（多份稿的变更汇总，按稿分节） |
| 8 | 某条变更缺 `impact` |

### S5 设计系统浏览器 · 第一批

**用途**：查这个项目的 token、图标、组件契约。
`umbra-tokens.json` 是 1,447 个叶子 / 810 KB，**不能全列出来**，必须是检索式的。
人用它对色、模型用同一份数据的检索接口。

**数据**：

```json
{
  "tokens": [
    { "path": "color.semantic.danger.soft", "value": "var(--danger-soft)",
      "resolved": "#FBE9E7", "kind": "color", "note": "平底上的失败态底色" },
    { "path": "space.gap.row", "value": "10px", "kind": "space" }
  ],
  "icons": [ { "name": "log.retry", "size": 16, "viewBox": "0 0 16 16", "d": "M8 2…" } ],
  "components": [
    { "name": "PC 空态", "file": "PC 空态.dc.html", "summary": "空 / 失败 / 离线三态的占位卡",
      "props": [
        { "name": "kind", "type": "'empty'|'error'|'offline'", "editor": "enum" },
        { "name": "title", "type": "string", "editor": "text" },
        { "name": "onAction", "type": "()=>void", "editor": null }
      ],
      "states": ["empty", "error", "offline"] }
  ]
}
```

`kind` 决定 token 怎么展示：`color` 要色块、`space` 要标尺、
`type` 要示例文字、`elevation` 要投影示例。

**状态清单**：

| # | 态 |
| --- | --- |
| 1 | token 检索有结果 |
| 2 | token 检索无结果 |
| 3 | 三个分类（token / 图标 / 组件）的切换 |
| 4 | 某个 token 只有 `value` 没有 `resolved`（别名链没解开） |
| 5 | 组件的 props 里有 `editor: null` 的（回调，不可调） |
| 6 | 图标很多（142 个）时的网格密度 |
| 7 | 项目没有配 `icons`（字段缺失） |

### S7 props 面板 · 第二批（同上）

组件稿单开时，把 `props` 里 `editor` 非 `null` 的项渲染成控件，改了就重渲染。
`editor` 取值：`text` | `enum` | `boolean` | `number` | `null`（不给控件）。

⚠️ 一条规矩：**演示态的切换钮不要放进 props 面板**。
一个状态两个入口，点下去不知道哪一个会生效。

## 六、答复与已定事项（第一轮）

Claude Design 对 §五 逐条给了倾向，下面是定下来的结果。
**六条采纳它的倾向，一条改（S3）。** 往后以这一节为准，§五 只作过程记录。

### 6.1 第一轮的范围其实是「S1 + S2（含 S3 的侧栏形态）+ tokens」

因为第 3 题定了 S3 是 S2 里的常驻侧栏，所以 S2 这一份稿必须把侧栏的
**折叠态与展开态**一起画出来，否则下一轮出 S3 时会反过来改 S2 的布局。

这一轮要交的是：

- `ui/S1-稿件索引.dc.html`（列表视图 + 墙视图）
- `ui/S2-单稿预览壳.dc.html`（含诊断侧栏的折叠 / 展开两态）
- `ui/_ds-tool/tokens.css`（浅色 + 深色两份值）
- `ui/Components/` 里这两屏用到的共用件

S1 + S2 已经覆盖几乎所有控件类型（列表行、卡片、徽章、搜索、筛选、分段控件、
顶栏、视口档位、缩放、可折叠侧栏、iframe 壳、空态），够定死形态。

### 6.2 为什么 S3 要两种形态

同意「常驻右侧、可折叠、不要浮层」，但**光有侧栏不够**：

- **侧栏形态**解决「改一条看一眼」—— 必须能和预览同屏，这是主形态；
- **整页形态**解决两件侧栏装不下的事：S3 状态清单第 4 条（几十条 error + warning
  混合，要分组要折叠），以及**整个项目跑一遍体检后的汇总**（每份稿一节）。

整页不是新屏，是同一份数据的宽版布局 —— 这和第 6 题「S3 同时是侧栏和整页，不算新屏」
是同一个意思，两题在这里对齐。

### 6.3 S6 的归属（第二批，现在不必画）

S4（变更清单）和 S6（版本对比）是同一份数据的两种投影：S4 是清单，S6 是画面。
所以 S6 到第二批时**做成 S4 里的一个视图切换**（清单 ↔ 画面），不要独立一屏。
这一轮不影响，只是别把 S4 的布局做成容不下第二个视图的样子。

### 6.4 ⚠️ 深色下的语义色对比度必须标注

工具界面有 `--tool-ok` / `--tool-warn` / `--tool-err` 三组语义色，
它们会同时以**平底上的字**和**实底上的字**两种方式出现（徽章 vs 填充块）。

Umbra 那套 token 在这里踩过坑并留了实测读数：深色下语义填充色提亮之后，
上面的白字只剩 2.76 / 3.35，双双不达标，因此才有了 `--on-warning` / `--on-danger` /
`--on-success` 和 `--danger-text` 这一族补丁 token。

**请在工具皮肤里一次做对**：

- 每组语义色给 `--tool-<sem>`（填充）、`--tool-<sem>-soft`（平底）、
  `--tool-on-<sem>`（实底上的字）、`--tool-<sem>-text`（平底上的字）四个值
- 浅色与深色各一套
- 在 token 的注释里写上关键组合的对比度读数（照 Umbra 的写法）

| C1 | **交付要能在断网的机器上打开。** 不许引任何 CDN，**包括网络字体** —— 用系统字体栈。⚠️ React 本地副本要靠 `window.__resources` 注入，**具体做法见 §7.2 ①** | 实现侧可能在内网 |

### 6.6 ⚠️ 不要用通用的「Claude 风格」提示词去纠偏

网上流传的那类提示词（"build a replica of the Claude workspace interface
using React and Tailwind CSS"）看着对味，但对这个项目**三处致命**：

| 它要什么 | 为什么不能要 |
| --- | --- |
| React 组件 + JSX | 稿是 `x-dc` 模板 + `{{ 洞 }}` + 逻辑类，不是 JSX（§2.1、§2.2） |
| Tailwind utility class | 样式一律写在 `style` 属性上，**明确不要 CSS 类与外部样式表**；Tailwind 还要构建或引 CDN，违反 C1 |
| 暖米白 + 燃橙色板（`#FBF9F6` / `#D97706`） | 那是 Umbra 那套暖灰 + 橙（`#DEDBD5` / `#E8590C`）的同族 —— §2.4 整条理由就是工具皮肤不能长成某个租户的样子 |
| 左历史 / 中对话 / 右 Preview-Code 的布局 | 那是「和大模型对话生成 artifact」的产品布局。UmbraDesign 第一阶段**没有对话面板**，调用方是模型；人看的是 S1–S4 |
| 预览区放一个占位 dashboard | 预览区是 iframe 装**真稿子**（§2.3） |

那类提示词里**唯一可迁移的**是克制的观感取向：薄边框、不用重投影、
层级靠留白与字重而不是靠描边和色块。这一条本来就和 Umbra 的动画与描边纪律一致，
可以作为观感方向转达；技术栈、布局、色板三样一律不采纳。

### 7.2 要改的三条

**① 断网打不开 —— C1 未达成。这是本文档的漏洞，不是设计侧的疏漏**

实测：外网请求全 abort → S1 一片空白，控制台
`[dc] failed to load React or boot: failed to load https://unpkg.com/react@18.3.1/…`。

根因：`support.js` 里 React 的 URL 是**硬编码常量**（`05` §1.2），
必须在 `<script src="./support.js">` **之前**注入 `window.__resources` 映射才能走本地副本。

> ⚠️ **修法已改，见 §7.5。** 结论是：**这一段不写进设计稿**，由工具在落盘时注入。
> 设计侧不需要改任何一份稿的 head。

**② 深色只能靠 props 切，外层挂属性无效**

根容器是 `data-tool-theme="{{ theme }}"`，而 `theme` 恒有值（`light` 或 `dark`）。
`tokens.css` 的注释写的是「深色挂 `[data-tool-theme="dark"]`，**可放在任意祖先上**」——
注释与实现矛盾：只要根容器输出 `light`，祖先上挂什么都被盖掉。

实测：在 `<html>` 上设 dark → body 背景变深，但界面内容全是浅色。

修法：浅色时**不输出这个属性**（让它继承），只在 dark 时输出 ——
`theme: P.theme === "dark" ? "dark" : null`。整值属性洞取不到时该属性不设置，
这正是 `03` §1.3 定的行为。改完 props 能切、外层也能切。

**③ 演示态胶囊只有数字 1–9**

现在要点一下、再看下面那行「当前演示态 空项目 · 一份稿都没有，给引导」才知道是哪一态，
九个态得点九次才摸清。胶囊上直接写态名（正常 / 空项目 / 无结果 / 未体检 / 有报错 /
超限 / 配置缺失 / 高密度），或至少 hover 出 `title`。
这是工具界面不是演示页，看的人要能直接跳到想看的那一态。

### 7.3 对设计侧三个问题的答复

1. **缩略图占位** —— 接受，就该是占位，真实缩略图由 `render_check` 产出（`00` §7.2）。
   但占位块的宽高比要和真实截图档位对齐（1440×900 → 16:10），
   否则换成真图时墙的栅格会跳。
2. **共用件不拆** —— 结论同意，但它给的理由有一条**不成立**：
   `dc-import` **能跨目录**，写相对路径 `name="../Components/X"` 即可（`03` §3.1），
   旧项目 `PC 端/Pages/` 就是两层目录且实测正常。
   成立的理由是后半句：当前重复都在 `sc-for` 里，拆了多一层没收益。

## 七之二 · 第一批改动的落地方式（§7.2 ① 的最终修法）

第一批的三条改动里，②（深色）和 ③（演示态名）由设计侧改，已完成。
**①（断网）改成由工具做，设计侧不动稿。**

### 7.5 为什么不改设计稿的 head

原方案是让设计侧在五份稿的 `<head>` 里手写 `window.__resources` 块。三条理由否掉它：

1. **设计侧取不到 React 的 UMD 副本**（无外网），而映射指向不存在的文件会让每屏白屏 ——
   设计侧自己也指出了这一点，判断是对的。
2. **设计侧的宿主自己会注入这张表**（`05` §1.1 的 `window.__resources` 钩子）。
   写进稿里在那边是冗余，甚至可能和宿主注入的表冲突。
3. **会造成源头分叉。** 设计稿的源头在设计侧，本机是同步副本。
   手写的那段只存在于本机，下次同步覆盖就没了，每轮都要重新手工加。

**所以它和 `@ds` 别名是同一类事：源头写抽象，落盘写具体**（`00` §5.2 的表）。
设计稿保持纯净，工具在落盘那一刻注入。
