# UmbraDesign · 01 产品需求文档

> 这一份说**为什么要有这套东西、它服务谁、必须做到什么**。
> MCP 工具契约见 `00`（实现主文档），运行时架构见 `02`，模板语义见 `03`，
> 缺陷与验收见 `04`，实测依据见 `05`，写稿规则见 `06`，变更交付见 `07`。
>
> **本版按 `05` 的实测读数改写过。** 旧版里三条被当成需求的"框架缺陷"
> 已经重新定性，见 §五。

---

## 一、解决的问题

设计侧要交付的不是图片，是**能被实现侧逐字照抄的界面事实**：
颜色取值、间距、状态分支、文案、交互时序。

用 Figma 交付会丢两样：**取值的精确性**（截图量不准）与
**状态的完整性**（静态画板装不下十几种态）。

所以定位是：**用 `.dc.html` 同时充当设计稿、规范出处和可运行原型**，
外面再包一层 MCP，让大模型能安全地写它、校它、并把变更讲清楚给实现侧。

---

## 二、使用者与阶段

| 阶段 | 调用方 | 通过什么 |
| --- | --- | --- |
| **第一阶段（当前）** | Claude / Codex 等大模型 | 本地 MCP server |
| 第二阶段 | Umbra 秘书 | 同一个 MCP server，另一个客户端 |
| 第二阶段 | 人（设计侧 / 产品侧） | props 面板、直接编辑、主题切换 |
| 全程 | 实现侧 | 打开稿取值 + 读 `CHANGELOG-设计侧.md` |

**第一阶段的调用方是模型，不是人。** 所有取舍以此为准：
宁可多一个结构化返回字段，不要多一个需要眼睛的界面。

**关键场景**：一个模块有十几种状态（空 / 加载 / 失败 / 权限不足 / 离线 / 到上限…），
它们必须**在同一份文件里可切换地存在**，而不是散成十几张图。

## 三、功能需求

### 3.1 稿件侧 · 必须有

| # | 需求 | 理由 |
| --- | --- | --- |
| F1 | `.dc.html` 无构建、无 npm 即可打开 | 交付零门槛。⚠️ 打开方式分两种，见 §四 |
| F2 | 模板 + 逻辑分离：HTML 模板挖洞，逻辑类算值 | 状态分支写在一处，不散落在模板里 |
| F3 | 条件渲染 / 列表渲染 | 状态切换、清单铺开 |
| F4 | 组件复用：一份稿引用另一份稿 | 十处共用的件只写一次 |
| F5 | 组件可传 children | 窗口骨架 + 各模块内容的组合 |
| F8 | 全局样式插槽（`<helmet>`） | 设计 token 只引一次 |

### 3.2 MCP 侧 · 必须有（第一批）

| # | 需求 | 出处 |
| --- | --- | --- |
| M1 | 按需检索设计系统：token / 图标 / 组件契约 | `00` §5.1 |
| M2 | 唯一写入口：归一化落盘 + 落盘即校验 + 落盘即留痕 | `00` §5.2 |
| M3 | 静态校验，诊断带 `code` / 文件 / 行号 / 洞名 / **改法建议** | `00` §六 |
| M4 | 渲染体检：真实 Chromium 判活、节点数、未解析的洞 | `00` §七 |
| M5 | 语义变更清单：四级分类 + `CHANGELOG-设计侧.md` | `07` |
| M6 | 入口页与浏览态静态服务（形态 A） | §四 |
| M7 | 设计系统可插拔：租户配置 + `@ds` 别名落盘时展开 | `00` §三 |

### 3.3 第二阶段（明确不在第一批）

| # | 需求 | 为什么推后 |
| --- | --- | --- |
| F6 | 流式渲染：内容一边写一边出现 | 第一阶段调用方是模型，一次性落盘，没有"边写边看"的人。**语法保留、实现推后**，见 `03` §八 |
| F7 | 可调参数（props）面板 | 给人用的 |
| F9 | 在渲染结果上直接改文案与颜色，写回源文件 | 模型场景下的等价物是 `patch_draft`（`00` §5.2），已在第一批 |
| F10 | 深浅色主题切换 | 给人用的 |
| F11 | 打印 / 导出 PDF | 给人用的 |
| F12 | `bundle_draft`：把 `dc-import` 内联成真单文件（形态 B） | 两点未验证，**不承诺**，见 `00` §九 |

### 3.4 明确不要

- **交付物不要构建步骤。** 任何需要 `npm install` 才能打开的 `.dc.html` 都不接受。
  ⚠️ 这一条约束**交付物**，不约束 MCP server 本身——后者可以有 `package.json`
  和依赖（`00` §二）。**两者在文档里不得混为一谈。**
- **不要 CSS 类与外部样式表**（设计 token 除外）：样式一律写在 `style` 属性上。
- **不要 JSX / TypeScript 写稿**：逻辑是普通 JS，浏览器直接吃。

## 四、非功能需求与交付形态

| 项 | 要求 | 依据 |
| --- | --- | --- |
| **渲染规模** | 一份稿 1,200 元素以内，超 1,500 必须拆 | ⚠️ 依据是**工程理由**，不是浏览器限制，见 §五 R3 |
| **离线** | 交付物只依赖 React + ReactDOM 的**本地副本**（142 KB），不走 CDN，不带 Babel | `05` §一、§五 |
| **诊断** | 一切错误以结构化结果回给调用模型，不许只进控制台 | §五 R2 |
| **落盘** | UTF-8 无 BOM、LF、末尾单个换行；内容相同 → 结果相同 | §五 R3 |

### 4.1 ⚠️ 打开方式分两种（这是硬约束，不是选择）

`support.js` 用 `fetch()` 取 `dc-import` 的兄弟稿，
而 **Chrome 不允许对 `file://` 发 fetch**（`05` §4.2 实测，`--allow-file-access-from-files`
也不管用）。所以 F1「双击即开」必须拆成两句：

| 稿的形态 | 打开方式 |
| --- | --- |
| **单文件稿**（零 `dc-import`） | 双击即开 ✅ |
| **带 `dc-import` 的稿** | 必须走本地 http ❌ 双击不行 |

这不是 bug，是浏览器安全策略，绕不过去。

### 4.2 交付形态

**形态 A「浏览态」—— 第一批做。**
整个租户目录 + 自动生成的入口页 `index.dc.html`，用 MCP 起的静态服务打开。
`dc-import` 全活，页面之间能跳。给设计侧和实现侧日常用。

> 源码组织**就该是 Web 项目的样子**：`index.dc.html` 作入口，页稿与组件分目录，
> `_ds/` 放设计系统。但**交付物不能变成需要构建的 Web 项目**（§3.4 第一条）。

**形态 B「单文件态」—— 第二批，未承诺。**
`bundle_draft` 把某一页的 `dc-import` 全部内联、资源全部内嵌，
产出一份真·双击即开的 `.html`。给要发出去、存档、贴到工单里的场合。

⚠️ 形态 B 有两点必须先验证才敢写进契约：
SVG 的 `<use>` / `<symbol>` 跨文件引用，`_ds_bundle.js` 里有没有相对路径的 fetch。

## 五、三条旧"需求"的重新定性

旧版 §五把三条现象当成"框架缺陷"，要求新框架做成「不可能发生」。
`05` 换了环境重测之后，三条里**两条推翻、一条无法复现**。
这里逐条交代——不改的话我们会照着幽灵设计。

### R1 事件洞取不到值 → 整页画不完 —— **未复现，降级为建议**

旧记录：模板上写 `onClick="{{ handler }}"` 而逻辑没给这个键，整页永远画不完，
不报错、控制台空白。

**实测（`05` §四）**：把 `PC 空态.dc.html` 的 `onAction: P.onAction ?? NOOP`
改回裸的 `P.onAction`（值确为 `undefined`），页面**照常渲染**，
读数与修复版完全相同（29 节点，`1+1` 正常）。`onSecondary` 同样去兜底，结果不变。

> **新地位**：给事件 / ref 洞兜底仍是好习惯（`06` §3.3），
> 但理由只是普通工程理由——`undefined` 传下去会让 ref 静默失效、排查费劲。
> **不再是硬需求，不要为它去改存量稿。**

保留的部分：**任何洞取不到值只影响那一处**，且整值属性洞取不到时
**该属性不设置**（相当于没写），不是设成 `undefined`；
并在诊断里给一条 `E_HOLE_UNRESOLVED`，带文件 / 行号 / 洞名。

### R2 渲染失败必须可诊断 —— **保留，并在 MCP 场景下加强**

这一条完全有效，而且在第一阶段更重要：**调用方是模型，模型看不到控制台。**

> **要求**：一切诊断以结构化结果回给调用方（`00` §四的统一信封），
> 每条带 `code` / `file` / `line` / `locator` / `message` / `fix`。
> 任何工具不得在返回 `ok: true` 的同时隐藏一条 error。
> 只往控制台打日志等于没报。

### R3 同样的输入必须给同样的结果 —— **根因未证实，但已从工程上堵死**

旧记录：同一份文件有时渲染有时卡死，取决于是工具直写还是脚本写入。
旧版自己也注明「这条还没自洽」。

`05` §1.1 找到了一个更可能的解释（**判断，非结论**）：
`support.js` 里有 `window.__resources` / `window.__resourceBlobs` 两个宿主注入钩子，
说明旧框架本来跑在一个带注入层和预览缓存的宿主里。
这一条**无法在 UmbraDesign 里复现或排除**，因为旧宿主不在我们手上。

> **处置**：不必先查清根因。`00` §5.2 已把 MCP 定为唯一写入口并强制归一化落盘
> （UTF-8 无 BOM / LF / 末尾单换行），**这从工程上堵死了整类可能**。
> 验收第 5 条保留，它现在是对归一化落盘的验收。

### R3-附 元素数阈值 —— **依据换了**

旧版写「单文件 1,500 个静态元素以内，超过就不渲染（本项目实测）」。

**实测（`05` §三）推翻**：6,514 个元素的 `Umbra PC 端.dc.html` 完整渲染，
12.1 秒出图，`1+1` 正常，控制台干净，截图逐项核对无误。
旧记录里「退回显示源码 + 中文乱码」的现象本身就排除了浏览器——
稿子头部有 `<meta charset="utf-8">`，Chrome 本地打开不可能乱码；
那是旧宿主的预览通道把文件按 `text/plain` 发出来了。

> **阈值保留，理由改成两条工程理由**：模型一次输出不了 175 KB；
> 语义变更清单的粒度就是文件粒度。详见 `00` §6.3。

### R4 多文件稿不能双击 —— **新增的硬约束**

见 §4.1。这一条四份旧文档里一条没提，而它是本轮**唯一稳定复现**的挂死原因。

## 六、验收标准

### 6.1 稿件渲染

1. `Umbra 设计规范.dc.html`（1,524 元素，零 `dc-import`）**双击**打开 → 渲染正确，控制台干净
2. `Umbra PC 端.dc.html`（6,514 元素，12 个 `dc-import`）**走本地 http** → 完整渲染，`1+1` 正常
3. 同一份稿被引用 10 次的子组件 → 只取一次文件
4. 两层以上目录的 `dc-import`（`PC 端/Pages/`）→ 正常
5. 同一份文件用三种方式经 `write_draft` 落盘 → 字节一致、渲染结果一致

### 6.2 诊断

6. 删掉一个 `onClick` 的洞 → `E_HOLE_UNRESOLVED`，点名洞名与行号，其余部分正常
7. 写错一个标签名 → `W_UNKNOWN_TAG`，报文件与行号
8. `dc-import` 指向不存在的文件 → `E_IMPORT_MISSING`，**显式报错，不是空占位**
9. 逻辑类某条早返回路径漏一个键 → `E_RETURN_PATH_GAP`，点名那条路径
10. 模板里写 `{{ a + b }}` → `E_HOLE_EXPRESSION`，拒绝落盘
11. `@ds` 展开后解析不到文件 → `E_DS_PATH`

### 6.3 变更交付

12. 不改一个字连续两次 `snapshot_draft` → 快照逐字节相同
13. 只重排一个渲染等价的容器 → 只有 L4，L1/L2/L3 全空
14. 模板中间插入一个 `<div>` → 后面的节点**不被全报成变更**
15. 给 props 加一个 `onRetry` → 报 L1 契约级
16. 连改四版同一个 `padding` → `get_changes_since` 只报首末值

### 6.4 离线

17. 断网打开单文件稿 → 正常渲染（React 走本地副本，无 Babel）
